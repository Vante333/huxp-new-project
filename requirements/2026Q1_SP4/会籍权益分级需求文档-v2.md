# 会籍权益分级需求文档（v2）

> 基于 v1 版本扩展，新增"同品类权益 tier 默认值兜底机制"。
> v1 文档：`.cursor/requirements/会籍权益分级需求文档.md`

## 一、会籍注册接口 `/v2/memberships`

### 1.1 新增 `scopeType` 字段

**字段说明：**
表示这个品类的权益是否支持分等级，根据SAAS权益模板中所选择的分组，去BOSS找到对应分组的`label`字段，根据这个字段来判断等级。

**判断逻辑：**
- 如果会籍模板下，同一个品类只要有权益勾了`tier`，即使勾的是同一个，那就是支持分等级。

**对应BOSS需求：** [PLATAIR-8195](https://dragonpass.atlassian.net/browse/PLATAIR-8195)

**字段定义：**
```
scopeType
1 = GLOBAL    // 不区分等级，权益可用于该 module 下的所有资源（旧）
2 = TIERED    // 资源按等级分组，权益使用受等级限制（新）
```

**字段逻辑对照表：**

| 字段 | 无权益分组（scopeType=1） | 有网络分组（scopeType=2） |
|------|-------------------------|-------------------------|
| `maxGuestsNextUse` | 正常计算 | 通过SAAS权益里的关联的网络分组ID，去BOSS找`label` |
| `allowedGuestsPerUsage` | 正常显示 | 返回`null` |
| `cardholderExclusiveEntitlements`等） | 正常返回 | 返回`null` |
| 总计 | - | 求和返回，表示总持卡人专属点数/总共享点数等 |

**响应示例：**
```json
{
  "entitlements": {
    "moduleExclusiveEntitlements": [
      {
        "module": 1,
        "scopeType": 1,
        "details": {
          "cardholderExclusiveEntitlements": 1,
          "guestsExclusiveEntitlements": 1,
          "sharedEntitlements": 0,
          "purchasedEntitlements": 0,
          "allowedGuestsPerUsage": 1,
          "maxGuestsNextUse": 1
        }
      }
    ]
  }
}
```

### 1.2 tier 默认值兜底逻辑（v2 新增）

**逻辑说明：**
- 会籍注册时，在判定 `scopeType` 的同时，需遍历该品类下所有权益
- 若品类被判定为 `scopeType=2`，则检查每条权益是否配置了 `tier`
- 未配置 `tier` 的权益，系统默认赋值 `tier=1`
- `scopeType` 的判定逻辑不变：同品类下只要有任意一个权益勾了 `tier`，即为 `scopeType=2`

**场景对照表：**

| 场景 | scopeType | tier 处理 |
|------|-----------|----------|
| 同品类所有权益均未配置 `tier` | 1（GLOBAL） | 不做处理 |
| 同品类所有权益均配置了 `tier` | 2（TIERED） | 按配置值处理 |
| 同品类部分权益配置了 `tier`，部分未配置 | 2（TIERED） | 未配置 `tier` 的权益自动归入 `tier=1` |

**统计逻辑：**
- 默认归入 `tier=1` 的权益与显式配置 `tier=1` 的权益合并计算
- 返回的权益总数统计逻辑不变，所有 tier（含默认 `tier=1`）的权益均参与求和

## 二、权益查询接口 `/v2/entitlements/search`

### 2.1 新增 `scopeType` 字段

**字段说明：**
表示这个品类的权益是否支持分等级，根据SAAS权益模板中的`tier`字段来判断。

**判断逻辑：**
- 如果会籍模板下，同一个品类有多个权益，其中某一个关联了有`label`的分组，那就是支持分等级。

**接口特性：**
- 对于分等级的客户来说，只返回各同类型权益明细的总和
- 各等级明细权益需要去`/v2/entitlements/details`查看

**字段逻辑对照表：**

| 字段 | 无权益分组（scopeType=1） | 有网络分组（scopeType=2） |
|------|-------------------------|-------------------------|
| `maxGuestsNextUse` | 正常计算 | 通过SAAS权益里的关联的网络分组ID，去BOSS找`label` |
| `allowedGuestsPerUsage` | 正常显示 | 返回`null` |
| 其他4个字段 | 正常返回 | 返回`null` |
| 总计 | - | 求和返回，表示总持卡人专属点数/总共享点数等 |

**响应示例：**
```json
{
  "entitlements": {
    "moduleExclusiveEntitlements": [
      {
        "module": 1,
        "scopeType": 1,
        "details": {
          "cardholderExclusiveEntitlements": 1,
          "guestsExclusiveEntitlements": 1,
          "sharedEntitlements": 0,
          "purchasedEntitlements": 0,
          "allowedGuestsPerUsage": 1,
          "maxGuestsNextUse": 1
        }
      }
    ]
  }
}
```

### 2.2 tier 默认值兜底逻辑（v2 新增）

**逻辑说明：**
- 查询返回的仍为各同类型权益明细的总和（与现有逻辑一致）
- 计算总和时，需将默认归入 `tier=1` 的权益纳入统计
- `scopeType` 判断及返回逻辑不变

**对照表：**

| 场景 | tier 值处理 | 总和统计 |
|------|-----------|---------|
| 品类内权益全部配置了 tier | 按配置值 | 所有 tier 求和 |
| 品类内部分权益未配置 tier | 未配置的默认 `tier=1` | 所有 tier（含默认 tier=1）求和 |

## 三、权益明细接口 `/v2/entitlements/details`

### 3.1 接口特性

**查询限制：**
- 只允许逐个品类查询
- 若没有的品类则返回提示语

**请求示例：**
```json
{
  "membershipId": "8888000066668888",
  "module": 1
}
```

**通用返回结构（无论是否分级）：**
- 2个`scopeType`都能使用这个接口
- `entitlements` 统一为数组结构

```json
{
  "membershipId": "8888000066668888",
  "module": 1,
  "scopeType": 2,
  "entitlements": [
    // ... 权益详情
  ]
}
```

### 3.2 场景A：无分级权益（scopeType = 1 GLOBAL）

**逻辑说明：**
- 和`search`接口返回逻辑完全一致，只是改为数组

**响应示例：**
```json
{
  "membershipId": "8888000066668888",
  "module": 1,
  "scopeType": 1,
  "entitlements": [
    {
      "details": {
        "cardholderExclusiveEntitlements": 2,
        "guestsExclusiveEntitlements": 1,
        "sharedEntitlements": 0,
        "purchasedEntitlements": 3,
        "allowedGuestsPerUsage": 1,
        "maxGuestsNextUse": 1
      }
    }
  ]
}
```

### 3.3 场景B：分级权益（scopeType = 2 TIERED）

**逻辑说明：**
- 按`tier`返回明细

**响应示例：**
```json
{
  "membershipId": "8888000066668888",
  "module": 1,
  "scopeType": 2,
  "entitlements": [
    {
      "tier": 1,
      "details": {
        "cardholderExclusiveEntitlements": 1,
        "guestsExclusiveEntitlements": 0,
        "sharedEntitlements": 0,
        "purchasedEntitlements": 0,
        "allowedGuestsPerUsage": 1,
        "maxGuestsNextUse": 1
      }
    },
    {
      "tier": 2,
      "details": {
        "cardholderExclusiveEntitlements": 2,
        "guestsExclusiveEntitlements": 1,
        "sharedEntitlements": 1,
        "purchasedEntitlements": 0,
        "allowedGuestsPerUsage": 2,
        "maxGuestsNextUse": 2
      }
    }
  ]
}
```

### 3.4 tier 默认值兜底逻辑（v2 新增）

**逻辑说明：**
- 当 `scopeType=2` 时，按 `tier` 返回明细
- 未配置 `tier` 的权益，与已显式配置 `tier=1` 的权益**合并到同一个 `tier=1` 节点**下展示
- 若品类下没有任何权益显式配置了 `tier=1`，但存在未配置 tier 的权益，仍需返回 `tier=1` 的节点（包含默认兜底的权益）

**场景示例：**

假设某品类下有 3 条权益：
- 权益A（非共享）：配置了 `tier=1`，持卡人专属 1 点
- 权益B（买点）：未配置 `tier`，买点 5 点 → 默认归入 `tier=1`
- 权益C（共享）：配置了 `tier=2`，共享 3 点

**响应示例：**
```json
{
  "membershipId": "8888000066668888",
  "module": 1,
  "scopeType": 2,
  "entitlements": [
    {
      "tier": 1,
      "details": {
        "cardholderExclusiveEntitlements": 1,
        "guestsExclusiveEntitlements": 0,
        "sharedEntitlements": 0,
        "purchasedEntitlements": 5,
        "allowedGuestsPerUsage": 1,
        "maxGuestsNextUse": 1
      }
    },
    {
      "tier": 2,
      "details": {
        "cardholderExclusiveEntitlements": 0,
        "guestsExclusiveEntitlements": 0,
        "sharedEntitlements": 3,
        "purchasedEntitlements": 0,
        "allowedGuestsPerUsage": 0,
        "maxGuestsNextUse": 0
      }
    }
  ]
}
```

> 说明：`tier=1` 节点中 `purchasedEntitlements=5` 来自未配置 tier 的买点权益（默认兜底归入）；`cardholderExclusiveEntitlements=1` 来自显式配置 tier=1 的非共享权益。

### 3.5 错误码

| 错误码 | 描述 | 英文提示 |
|--------|------|---------|
| 500.030.029 | 请求的 module不存在 | The specified module does not exist for this membership. |
| 500.030.007 | 无法获取权益明细（兜底） | Sorry, we're unable to retrieve the membership entitlements at the moment. Please try again later. |

## 四、编辑权益接口 `/v2/entitlements/update`

### 4.1 新增 `tier` 字段

**字段说明：**
- 选填字段，控制修改哪个等级的权益
- 只有存在分级权益的情况下，才能使用此字段

**请求示例：**
```json
{
  "membershipId": "8888000066668888",
  "module": 1,
  "tier": 3,
  "usageRestriction": 1,
  "quantity": 1,
  "purchasedQuantity": 2
}
```

### 4.2 验证规则

1. **不存在分级权益又给了`tier`字段**
   - 返回提示语：`500.030.026`
   - 提示信息：`Operation not allowed. Tiered entitlements are not enabled.`

2. **存在分级权益，但没给`tier`字段**
   - 返回提示语：`500.030.027`
   - 提示信息：`Tiered entitlements are enabled. Please specify the tier to be updated.`

3. **操作不存在的`tier`**
   - 返回提示语：`500.030.028`
   - 提示信息：`The specified tier does not exist.`

4. **特殊情况**
   - 如果没配`tier1`（默认兜底），又来操作`tier1`，提示：`500.030.028`
   - 对应`tier`需要存在对应的权益模板（买点、大客户等）才能操作，否则返回兜底提示语

### 4.3 tier 默认值兜底对 update 的影响（v2 新增）

**核心原则：** 默认兜底机制是**读侧行为**，`update` 接口的 tier 合法性判断以**显式配置**为准，默认兜底归入的 `tier=1` **不作为**合法操作依据。

**验证规则补充说明：**

| 验证规则 | 现有行为 | 兜底机制补充 |
|---------|---------|------------|
| 不存在分级权益又给了 `tier` 字段 | 返回 `500.030.026` | 不变 |
| 存在分级权益，但没给 `tier` 字段 | 返回 `500.030.027` | 不变 |
| 操作不存在的 `tier` | 返回 `500.030.028` | 不变 |
| 没配 `tier1` 又来操作 `tier1` | 返回 `500.030.028` | **保留**。若品类下存在未配置 tier 的权益（读侧已默认归入 tier=1），update 仍视 tier=1 为不存在；仅当品类下有**显式配置** tier=1 的权益时才合法 |

**场景对照表：**

| 场景 | 操作 tier=1 | 结果 |
|------|-----------|------|
| 品类内存在**显式配置** `tier=1` 的权益 | 合法 | 正常操作 |
| 品类内部分权益未配置 tier（读侧默认归入 tier=1），但**无显式配置** `tier=1` 的权益 | 非法 | 返回 `500.030.028` |
| 品类内所有权益均有显式 tier，但无 `tier=1`（如仅有 tier=2、tier=3） | 非法 | 返回 `500.030.028` |
| 品类内既有**显式配置** `tier=1`，又有未配置 tier 的权益 | 合法 | 正常操作 |

### 4.4 三种权益类型的入参约束（v2 新增）

**入参约束表：**

| 权益类型 | update 允许入参 | 不可传 |
|---------|----------------|-------|
| 非共享权益（持卡人专属/客人专属） | `quantity` | `purchasedQuantity` |
| 共享权益 | `quantity` | `purchasedQuantity` |
| 买点权益 | `purchasedQuantity` | `quantity` |

**与 tier 交叉的校验逻辑：**

当指定 `tier` 操作时，系统需同时校验：
1. 该 `tier` 是否为显式配置（合法性）
2. 该 `tier` 下是否存在对应类型的权益模板（买点模板 / 非共享模板 / 共享模板）
3. 入参是否匹配权益类型（`quantity` vs `purchasedQuantity`）

### 4.5 返回逻辑

- 返回与`search`接口返回一致
- 除了新增`scopeType`外不变
- 返回的是所有`tier`总数

## 五、资源查询接口

### 5.1 需求背景

**对应BOSS需求：** [PLATAIR-8195](https://dragonpass.atlassian.net/browse/PLATAIR-8195)

**数据来源：**
- 资源数据来源于BOSS项目和价格清单
- 即使权益进行了分组，总资源范围是不变的
- 权益分组会影响资源中的`tier`字段

**查询逻辑：**
- 如果不加`Tier`查询，就是查BPN项目级数据
- 如果加`Tier`查询，就要拿网络分组ID+项目ID做查询

**涉及接口：**
- `https://developer-sandbox.dragonpass.com/api/v2/resources`

### 5.2 字段改造

**改造内容：**
- `tier`字段之前是写死为`1`的
- 现在需要改为读取BOSS网络分组的`tier`

## 六、告警机制

### 6.1 告警触发条件

1. **资源多分组告警**
   - 如果某个资源同时在N个分组，触发告警

2. **资源等级不完整告警**
   - 如果一个项目下，任意一个资源有等级了
   - 但有某些资源不存在某个等级分组，也触发告警

### 6.2 告警目的
- 确保资源分级的完整性和一致性
- 避免因资源分级不完整导致的权益使用问题

## 七、总结（v1）

### 7.1 核心变更点

1. **新增`scopeType`字段**：标识权益是否支持分级
2. **新增`tier`字段**：在编辑接口中指定操作等级
3. **资源`tier`字段改造**：从写死改为动态读取BOSS网络分组
4. **新增权益明细接口**：支持按等级查询权益明细
5. **告警机制**：确保资源分级的完整性和一致性

### 7.2 接口影响范围

| 接口 | 变更内容 | 影响 |
|------|---------|------|
| `/v2/memberships` | 新增`scopeType`字段 | 会籍注册时确定权益类型 |
| `/v2/entitlements/search` | 新增`scopeType`字段 | 权益查询时返回总和 |
| `/v2/entitlements/details` | 新增接口 | 查询各等级权益明细 |
| `/v2/entitlements/update` | 新增`tier`字段 | 编辑指定等级的权益 |
| `/v2/resources` | `tier`字段改造 | 资源等级动态读取 |

### 7.3 注意事项

1. **向后兼容**：旧版`scopeType=1`（GLOBAL）保持原有逻辑
2. **数据一致性**：分级权益需要确保各等级权益模板的完整性
3. **告警监控**：及时处理资源分级异常情况
4. **接口调用**：分级权益客户需调用不同接口获取完整信息

## 八、同品类权益 tier 默认值兜底机制（v2 新增）

### 8.1 需求背景

在 SAAS 权益模板配置过程中，存在以下场景：同一品类（module）下，部分权益配置了 `tier`（网络分组），而部分权益未配置 `tier`。

根据现有 `scopeType` 判断逻辑，只要同一品类下存在任意一个权益关联了带有 `label` 的分组，该品类即被标记为 `scopeType=2`（TIERED）。但此时未配置 `tier` 的权益缺少等级归属，需要进行默认值兜底处理。

### 8.2 核心规则

> 当同一品类被判定为 `scopeType=2`（TIERED）时，若该品类下存在未显式配置 `tier` 的权益，则这些权益在**读侧**（查询/展示）自动归入 `tier=1`，作为默认兜底等级。

**读写行为差异：**

| 行为侧 | 兜底机制作用 | 说明 |
|--------|------------|------|
| 读侧（memberships / search / details） | 生效 | 默认 tier=1 的权益参与总和统计和明细展示 |
| 写侧（update） | 不生效 | tier 合法性仅以显式配置为准，默认兜底的 tier=1 不可操作 |

### 8.3 三种权益类型说明

| 权益类型 | update 允许入参 | 说明 |
|---------|----------------|------|
| 非共享权益（持卡人专属/客人专属） | `quantity` | 不可传 `purchasedQuantity` |
| 共享权益 | `quantity` | 不可传 `purchasedQuantity` |
| 买点权益 | `purchasedQuantity` | 不可传 `quantity` |

### 8.4 配置场景与各接口行为

#### 场景一：非共享 tier=1，共享 tier=2，买点未配置 tier

**配置：**

| 权益 | tier 配置 | 实际归属 |
|------|----------|---------|
| 非共享权益（持卡人专属 2 点，客人专属 1 点） | 显式 tier=1 | tier=1 |
| 共享权益（共享 3 点） | 显式 tier=2 | tier=2 |
| 买点权益（买点 5 点） | 未配置 tier | 读侧默认归入 tier=1 |

**memberships / search 响应（总和）：**
```json
{
  "module": 1,
  "scopeType": 2,
  "details": {
    "cardholderExclusiveEntitlements": 2,
    "guestsExclusiveEntitlements": 1,
    "sharedEntitlements": 3,
    "purchasedEntitlements": 5,
    "allowedGuestsPerUsage": null,
    "maxGuestsNextUse": null
  }
}
```

**details 响应（按 tier 明细）：**
```json
{
  "membershipId": "8888000066668888",
  "module": 1,
  "scopeType": 2,
  "entitlements": [
    {
      "tier": 1,
      "details": {
        "cardholderExclusiveEntitlements": 2,
        "guestsExclusiveEntitlements": 1,
        "sharedEntitlements": 0,
        "purchasedEntitlements": 5,
        "allowedGuestsPerUsage": 1,
        "maxGuestsNextUse": 1
      }
    },
    {
      "tier": 2,
      "details": {
        "cardholderExclusiveEntitlements": 0,
        "guestsExclusiveEntitlements": 0,
        "sharedEntitlements": 3,
        "purchasedEntitlements": 0,
        "allowedGuestsPerUsage": 0,
        "maxGuestsNextUse": 0
      }
    }
  ]
}
```

**update 行为：**

| 操作 | 入参 | 结果 | 原因 |
|------|------|------|------|
| tier=1, quantity=5 | `quantity` | 成功 | tier=1 有显式配置的非共享权益 |
| tier=1, purchasedQuantity=5 | `purchasedQuantity` | 失败 | tier=1 下买点权益是默认兜底的，非显式配置 |
| tier=2, quantity=5 | `quantity` | 成功 | tier=2 有显式配置的共享权益 |
| tier=2, purchasedQuantity=5 | `purchasedQuantity` | 失败 | tier=2 下无买点权益模板 |

#### 场景二：非共享 tier=1，共享 tier=1，买点 tier=2

**配置：**

| 权益 | tier 配置 |
|------|----------|

### 8.5 各接口兜底机制作用总结

| 接口 | 兜底机制的作用 |
|------|--------------|
| `/v2/memberships` | 注册时，未配置 tier 的权益默认归入 tier=1，参与总和统计 |

## 九、总结（v2）

### 9.1 v2 核心变更点

1. **新增 tier 默认值兜底机制**：`scopeType=2` 的品类下，未显式配置 `tier` 的权益在读侧自动归入 `tier=1`
2. **读写行为差异**：兜底机制仅影响读侧（memberships / search / details），写侧（update）的校验逻辑不变
3. **合并计算**：默认 `tier=1` 的权益与显式 `tier=1` 的权益在读侧合并计算和展示
4. **入参约束明确**：买点权益只能使用 `purchasedQuantity`，其余权益只能使用 `quantity`
5. **校验规则全部保留**：`/v2/entitlements/update` 的现有校验逻辑（500.030.026/027/028）不做移除

### 9.2 v2 接口影响范围

| 接口 | v2 新增影响点 |
|------|-------------|
| `/v2/memberships` | 注册时，未配置 tier 的权益默认归入 tier=1，参与总和统计 |
| `/v2/entitlements/search` | 查询总和时，默认 tier=1 的权益纳入统计 |
| `/v2/entitlements/details` | 明细展示时，默认 tier=1 的权益与显式 tier=1 合并到同一节点展示 |
| `/v2/entitlements/update` | tier=1 的合法性判断需注意：仅靠兜底归入的 tier=1 不可操作；需有显式配置 |

### 9.3 v2 注意事项

1. **兜底时机**：默认值赋值发生在系统层面（读取权益模板时），不改变 SAAS 模板中的原始配置数据
2. **向后兼容**：`scopeType=1`（GLOBAL）的品类不受影响，不触发兜底逻辑
3. **读写差异预期**：`details` 可能展示 `tier=1` 节点但 `update` 拒绝操作，这是预期设计
4. **数据一致性**：建议 SAAS 配置时给予提示，引导用户为所有权益配置 tier，减少对兜底机制的依赖
