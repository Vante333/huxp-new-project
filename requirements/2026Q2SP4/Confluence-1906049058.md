# 订单流支持【真现金支付】【第三方权益】

## 一、概述

### 1.1 支持品类

一期：Lounge PB + FT

二期：其他（待定）

### 1.2 主要改动内容

商品选择部分：将原支持的【项目支付】+【现金支付】进行定义改造，支持按 api 参数进行动态选择，并在现金支付的前提下，额外支持权益抵扣（含第三方）；

订单流链路部分：将分为"计算价格"、"创建订单"、"订单确认与支付"、"订单分发"、"订单履约"五大块；

| 模块 | 改动 |
| --- | --- |
| 计算价格 | 改为调用 saas 接口计算价格；新增金额部分数据返回 |
| 创建订单 | 根据入参动态选择商品；金额部分信息基于 saas 计算好的数值去下单，不再需要自己计算 |
| 订单确认与支付 | 根据支付类型决定是否要调用 saas 接口拉起收银台；不再需要由 api 侧来更新支付相关数据，改为由 saas 监听 pci 的消息 |
| 订单分发 | 基本没变 |
| 订单履约 | 基本没变 |

### 1.3 参考资料

saas 的需求：

现金支付+权益支付（DP权益+第三方权益）

saas 的技术方案：

订单流（现金+第三方权益）

新订单流对接

## 二、需求

### 2.1 根据入参动态选择商品

影响【计算价格】和【创建订单】2 部分

### 2.1.1 初始化 saas 新增兑换类型的需求：PS20-10

- 当前 memberhsip 下，配置的商品（Lounge PB+FT）都是【现金（权益抵扣）】，需要统一初始化为【客户预收费】，下单也是找【客户预收费】。
- 当前 E-pass 下，配置的商品（Lounge PB+FT）都是【权益支付】，保持不变。如果需要支持现金支付，则新配置商品，根据 API 接口的入参决定得用哪个商品。

总结：每个品类都需要初始化 3 个商品：

- 客户预售费
- 权益支付
- 现金（支持权益抵扣）

总结：

| 商品类型 | DP收款 | 客户预收款 | 纯权益支付 |
| --- | --- | --- | --- |
| E-pass | ✅ DP_COLLECT + toUseUsageCount | ❌ 不支持 | ✅ 原逻辑 |
| Membership | ✅ DP_COLLECT + cashPaymentApplied=false | ✅ CLIENT_COLLECT + cashPaymentApplied=true | ✅ cashPaymentApplied=false |

| 参数 | 适用范围 | 说明 |
| --- | --- | --- |
| cashPaymentApplied | Membership/E-pass | 是否存在现金支付部分。false = 全权益支付或 DP 收款模式。true = 存在客户自行收款部分。 |
| toUseUsageCount | E-pass | 本次订单计划使用的 Usage 数量，仅用于 E-pass 的权益抵扣场景。 |
| toUseEntitlementCount | Membership | 本次订单计划使用的权益数量，仅用于 Membership 的权益抵扣场景。 |
| cashier.paymentMode=DP_COLLECT | E-pass / Membership | DP 负责向用户收款 |
| cashier.paymentMode=CLIENT_COLLECT | Membership | 客户已向用户收费，DP 不收款，仅记录和扣减权益。 |
| 不传 cashier | E-pass / Membership | 表示无现金支付流程。 |

### 2.2 预览订单接口

预览订单这步，saas 不会检验会籍状态和权益点数，api 侧需要保留权益与会籍状态检验，分别调用：

- saas 权益计算接口 - 获取权益使用明细
- saas 算价接口 - 获取 payment object

### 2.2.1 payment object 返回内容

```json
"payment": {
    "currency": "USD",
    "price": {
        "originalAmount": 120,
        "deductionAmount": 40,
        "payableAmount": 80
    },
    "charges": [
        {
            "type": "BASE_PRICE",
            "details": [
                {
                    "paxType": "CARDHOLDER",
                    "quantity": 1,
                    "unitPrice": 50,
                    "amount": 50
                },
                {
                    "paxType": "GUEST",
                    "quantity": 1,
                    "unitPrice": 50,
                    "amount": 50
                }
            ]
        },
        {
            "type": "PREBOOKING_FEE",
            "details": [
                {
                    "paxType": "CARDHOLDER",
                    "quantity": 1,
                    "unitPrice": 10,
                    "amount": 10
                },
                {
                    "paxType": "GUEST",
                    "quantity": 1,
                    "unitPrice": 10,
                    "amount": 10
                }
            ]
        }
    ],
    "deductions": [
        {
            "strategy": "ENTITLEMENT",
            "appliedTo": "BASE_PRICE",
            "details": [
                {
                    "paxType": "CARDHOLDER",
                    "quantity": 1,
                    "unitAmount": -20,
                    "amount": -20
                },
                {
                    "paxType": "GUEST",
                    "quantity": 1,
                    "unitAmount": -20,
                    "amount": -20
                }
            ]
        }
    ]
}
```

> 字段映射：`originalAmount` → originalTotalAmount；`deductionAmount` → equityDiscountFee；`payableAmount` → totalAmount；`unitPrice` 取 overNumFee；PREBOOKING_FEE 的 unitPrice 取 prebookFee 除订单总人数。

charges 下 type 的枚举：

| 枚举 | 描述 |
| --- | --- |
| BASE_PRICE | 超人次价格 |
| PREBOOKING_FEE | 预约服务 |
| SERVICE_FEE | 预留的，现在没有，其他服务费 |

deductions 下 strategy 的枚举：

| 枚举 | 描述 |
| --- | --- |
| ENTITLEMENT | 权益抵扣，现在有 |
| COUPON | 预留的，现在没有，优惠券抵扣 |
| PROMOTION | 预留的，现在没有，活动抵扣 |

deductions 下 appliedTo 的枚举：

| 枚举 | 描述 |
| --- | --- |
| BASE_PRICE | 只抵扣超人次价格，现在有 |
| PREBOOKING_FEE | 预留的，只抵扣预约费，现在没有 |
| BASE_AND_PREBOOKING | 预留的，抵扣超人次+预约费，现在没有 |

## 2.3 拉起 DP 收银台

### 2.3.1 是否要拉起收银台

与 2.1.2 逻辑是一样的

### 2.3.2 创单后返回

对于需要拉起收银台的订单，创单后都是返回 status=9 PendingPayment

其他内容跟 pending 状态的返回一致

### 2.3.3 获取支付链接接口

```text
POST /v2/orders/payments
```

请求，现在只支持 H5_CASHIER，以后可能有 COF

同一个 DP00000000000001，不同的 requestId 多次去请求 PCI，支付链接由 PCI 控制是否一致

目前是只能请求 1 个链接的，问一下 saas 有没有做幂等

```json
{
  "orderId": "DP00000000000001",
  "ePassId": "DP00000000000001",
  "paymentMethod": "H5_CASHIER",
  "returnUrl": "https://example.com/payment/return",
  "cancelUrl": "https://example.com/payment/cancel"
}
```

H5 的：

```json
{
  "orderId": "DP00000000000001",
  "status": 9,
  "paymentStatus": "PendingPayment",
  "paymentAction": {
    "type": "REDIRECT",
    "url": "https://cashier.example.com/pay/xxx",
    "validUntil": "时间戳"
  }
}
```

COF 的：

```json
{
  "orderId": "DP00000000000001",
  "status": 9,
  "paymentStatus": "",
  "paymentAction": {}
}
```

> COF 的 paymentStatus 只有完成或失败。
