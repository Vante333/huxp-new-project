## 评审总结

### 整体评价

该方案在**性能优化方向**（本地缓存 + Redis、program 拆 project 粒度）表述清楚，对现状问题与目标指标有定量描述。但从**可测试性与一致性**看，文档对「配置/资源变更后数据如何在新请求中生效」未形成闭环：本地缓存命中路径与 MQ 刷新叙述之间存在矛盾风险，Redis 侧 key 的失效策略也未写明。另缺少可复现的压测验收口径与上线灰度/观测设计。结论：**建议补充后再进入开发联调与性能验收**。

### 测试风险提示

1. **一致性窗口**：在未明确 L1/Redis 失效策略前，重点验证「Program 配置变更后」各节点 `/v2/resources` 等接口的返回是否滞后及最长滞后时间。
2. **并发与冷启动**：关注本地 miss 风暴、Redis miss、下游 Boss 调用放大；需配合研发确认是否有 single-flight 或等价机制。
3. **环境依赖**：压测需接近生产的 program/project 规模与语种维度，否则 TPS/P95 指标不具备可比性。
4. **回归建议（方案已列接口）**：至少覆盖 `/v2/resources`、`/v2/transportHubs`、`/v2/search`、`/v2/search/modules` 在正常、变更后、多节点、高并发四类场景下的功能与性能表现。

#### 发现的问题

##### 问题 1: 本地缓存命中时可能阻断 MQ 触发的「刷新」效果
- **严重等级**：🔴 严重
- **评审维度**：方案正确性
- **检查项编号**：3.2-①、5.2-②、6.1-③
- **问题描述**：文档称消费消息后调用 `getNetworkListByProgram` 重新加载，但伪代码在本地缓存命中时直接记录日志并继续使用旧值，未体现 invalidate、bypass 或版本切换。
- **原文引用**：
  > `Map> projectNetwork = localCache.get(cacheKey);` 命中分支 `log.info("Local cache hit...` 与未命中分支内 `localCache.put`（见 `tech-docs/2026_Q2SP2/Resource.md` 第 5 章伪代码）。
  >
  > `收到消息后...调用 networkResourceWithCacheService.getNetworkListByProgram(...) 重新加载`（见同文档第 6 章）。
- **测试影响**：无法保证「变更后读接口立即/在承诺时间内反映新配置」。
- **修改建议**：
  - **建议类型**：补充 / 修正
  - **修改位置**：第 5 章与第 6 章之间增加「变更后缓存处理」
  - **建议内容**：明确 MQ 消费后对 L1 的处理（按 key 删除、全量清理、强制走 Redis 等）及最大可见延迟。

##### 问题 3: 并发 miss 时可能放大回源
- **严重等级**：🟡 一般
- **评审维度**：性能与并发
- **检查项编号**：1.3-②、6.2-②
- **问题描述**：未见 `get(key, loader)`、互斥、分布式锁等描述，多线程同时 miss 同一 key 时可能并发回源。
- **原文引用**：
  > 本地未命中分支内直接调用 `getNetworkListBySingleProject` 并 `localCache.put`（同文档第 5 章）。
- **测试影响**：冷启动或热点 program 下性能抖动，TPS 目标可能不稳定。
- **修改建议**：
  - **建议类型**：补充
  - **修改位置**：第 5 章「核心实现」
  - **建议内容**：写明并发控制策略及监控指标（回源并发数、miss 率）。

##### 问题 4: 预警与资源变更检测触发时机不当
- **严重等级**：🟡 一般
- **评审维度**：方案正确性
- **检查项编号**：2.1-②、3.1-②
- **问题描述**：`warnNetworkGroup`、`detectResourceChanges` 位于单 project 的 miss 分支内，且此时聚合 `result` 尚不完整，易导致重复执行或基于部分数据判断。
- **原文引用**：
  > `// 预警分组` 与 `// 异步检测资源变更` 位于 `if (projectNetwork == null \|\| projectNetwork.isEmpty())` 分支内，其后才是「合并结果」（见 `tech-docs/2026_Q2SP2/Resource.md`）。
- **测试影响**：告警类用例预期次数与输入数据难以定义。
- **修改建议**：
  - **建议类型**：修正
  - **修改位置**：第 5.2 节伪代码与文字说明
  - **建议内容**：将副作用移至全量合并完成后；说明异步/幂等语义。

#### 测试关注点

1. L1 命中与未命中组合下的返回一致性。  
2. 多线程并发请求同一 program 时的下游调用次数。  

#### 模块小结

实现思路可理解，但**一致性与副作用位置**需在方案层先闭合，否则测试无法写死预期。
