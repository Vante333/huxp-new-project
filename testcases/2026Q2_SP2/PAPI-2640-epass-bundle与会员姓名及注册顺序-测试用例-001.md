# PAPI-2640【ePass-bundle与会员姓名】注册顺序测试用例

## 测试范围说明

- rc: 基于 `requirements/2026Q2_SP2/PAPI-2640.md` 与 [PAPI-2640-epass-bundle与会员姓名-测试分析](./PAPI-2640-epass-bundle与会员姓名-测试分析.md)；业务规则以需求原文为准。
- rc: **ePass、bundle 创建**所对应的 **HTTP 路径、方法、请求体字段名（姓名字段）、成功体与业务错误码** 均以 **APIFOX** 及技术方案为准；本文件步骤中「创建 ePass / 创建 bundle / 查询会员或会籍」处执行人替换为实际接口调用。
- rc: 与 [PAPI-2568-AeroBlue注册字段与clientUserId重复注册-测试用例-001](./PAPI-2568-AeroBlue注册字段与clientUserId重复注册-测试用例-001.md) 同迭代回归时，**重复注册策略与姓名不一致拒绝对齐 APIFOX**，不因 PAPI-2640 编排修复而弱化。

## EpassThenBundle（顺序A：先ePass后bundle）

### tc-p1: 同一clientUserId先成功创建ePass再创建bundle成功且会员姓名与ePass后一致

pc: 目标租户与 program 下具备合法 **ePass 创建**与 **bundle 创建**能力；使用同一 `clientUserId`；ePass 创建报文携带与 APIFOX 一致的非空姓名字段

- 调用 **ePass 创建**接口完成创建
  - 成功；会员侧（或查询接口返回）姓名为非空且与请求约定一致
- 使用同一 `clientUserId` 调用 **bundle 创建**接口（其余必填合法）
  - **bundle 创建成功**（HTTP 与业务码符合 APIFOX 成功约定）
- 调用 **会员或会籍查询**类接口读取该用户姓名相关字段
  - 姓名与 **ePass 成功后** 已持久化的取值一致，**未**因 bundle 创建被清空或变为仅空格等「空名」形态

### tc-p1: 会员已有非空姓名时bundle请求中姓名字段为空或缺省仍成功且会员名不被写成空

pc: 与上条相同前置，且 ePass 成功后会员名为已知非空值

- 调用 **bundle 创建**接口，将姓名字段置为 APIFOX 允许的空 / 缺省形态（若接口拒绝缺省则本用例改为「预期失败」并与产品对齐）
  - bundle 仍 **创建成功**
- 再次查询会员姓名
  - 仍为 **ePass 阶段的非空姓名**，未被写成 null、空串或仅空格（与需求「不将空名字 set 到会员」一致）

### tc-p2: 会员已有非空姓名时bundle请求携带与会员不一致的另一组非空姓名时行为符合产品口径

pc: 会员侧已为姓名 A；bundle 报文携带姓名 B（A≠B，均非空）

- 调用 **bundle 创建**接口
  - 行为与 **产品/APIFOX** 约定一致：或为成功且会员名按约定保留 A / 更新为 B / 或业务拒绝并返回约定错误码（需求未写非空冲突口径，执行前需确认预期并固化本步骤断言）

### tc-p3: 仅创建ePass不创建bundle时行为与改造前一致

pc: 与主流程相同环境，仅走单产品

- 仅调用 **ePass 创建**接口
  - 成功语义、字段校验与现网或 APIFOX 基线一致，无回归异常

## BundleThenEpass（顺序B：先bundle后ePass）

### tc-p1: 先bundle后ePass且ePass携带合法姓名时会员侧姓名与请求一致

pc: 同一 `clientUserId` 先完成 **bundle 创建**；查询确认会员姓名为「空名」形态（与研发约定：空串、未返回、或占位值等）

- 调用 **ePass 创建**接口，携带 APIFOX 要求的合法姓名字段（与 bundle 阶段空名形成对比）
  - **ePass 创建成功**
- 查询会员姓名
  - 与本次 ePass 请求中的姓名语义一致（或经产品归一化后与之一致）

### tc-p1: ePass写名后依赖会员展示名的查询或列表与之一致

pc: 已完成上条「bundle→ePass 且已写名」

- 调用任意依赖「会员展示名」的 **查询/列表** 类接口（与项目约定清单一致，至少覆盖一种）
  - 展示名与已写入会员的姓名 **一致**（需求：后续所有业务以此名字为准）

### tc-p2: 会员仍为空名时ePass创建不传姓名时失败或按APIFOX缺省规则处理

pc: bundle 后会员仍为空名；构造 **不传姓名** 的 ePass 创建报文

- 调用 **ePass 创建**接口
  - 若产品要求「必须带名写入」：返回明确业务失败与错误码；若 APIFOX 允许缺省：成功形态与缺省规则一致且无静默脏数据

### tc-p3: 仅创建bundle不创建ePass时行为与改造前一致

pc: 与主流程相同环境

- 仅调用 **bundle 创建**接口
  - 成功语义与会员空名表现与基线一致，无回归异常

## MemberNameConcurrency（并发与重试）

### tc-p2: 同一clientUserId极短时间相邻调用ePass与bundle时会员名终态符合顺序规则且无脏写

pc: 具备并发或快速连续请求条件；数据准备满足可分别触发 ePass 与 bundle 创建

- 按「先 ePass 后 bundle」与「先 bundle 后 ePass」各执行一组 **快速连续** 调用（或并行一次，以安全环境为准）
  - 终态会员名符合对应顺序下的需求规则，无中间态暴露导致的错误下单或非法展示（具体断言依赖查询接口可得字段）

### tc-p3: 创建接口在可重试错误后重试成功时会员名不被重复或错误覆盖

pc: 模拟或选取允许安全重试的失败后再成功路径（若存在）

- 首次失败后使用 **相同业务幂等键或相同报文** 重试至成功
  - 会员姓名与业务规则一致，无重复写、无回滚残留不一致

## CrossRef_P2568（与重复注册策略交叉冒烟）

### tc-p2: 在租户允许同clientUserId多会籍时顺序A主路径仍成功且不与REG姓名不一致规则冲突

pc: 租户与 program 满足 PAPI-2568 中「同 clientUserId 第二次注册成功」类前置；会员已有名

- 按 **EpassThenBundle** 中 tc-p1 完成 ePass 再 bundle
  - bundle 成功；若同时触发「注册报文姓名与会员库不一致」类校验，行为以 **APIFOX** 为准且与 PAPI-2568 用例预期不矛盾
