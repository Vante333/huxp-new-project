## 1. 文档定位

- 原始测试分析：`D:\fenxi\API\2026_Q2\评审后\Q2_SP4\订单流支持真现金支付第三方权益测试分析.md`

- 预约费承担方：客户。

金额应使用 `Decimal`，禁止使用二进制 `float` 直接比较。接口返回金额统一先规范化为 `Decimal`，再按接口约定的小数位比较。

## 4. 人数和金额规则

当前核对数据统一使用预约人数3人：

- 持卡人 `CARDHOLDER.quantity=1`。
- 随行人 `GUEST.quantity=2`。
- `BASE_PRICE` 的人数和正向金额不随权益抵扣数量减少。

### BASE_PRICE

- 持卡人金额：`1 × 超人次单价`。
- 随行人金额：`2 × 超人次单价`。
- 合计：`3 × 超人次单价`。

### PREBOOKING_FEE

- 客户承担：面向用户的 `PREBOOKING_FEE.details=[]`，不计入用户应付金额。
- 用户承担：返回持卡人1人、随行人2人的明细，合计为 `3 × 预约单价`。
- 用户承担且预约价为0：保留人数结构时，各金额为0；最终以 SaaS 实际返回结构为准。

### deductions

- 使用权益0：`deductions=null` 或空数组。
- 使用权益1：只抵扣持卡人的一份 `BASE_PRICE`。
- 使用权益3：抵扣持卡人一份和随行人两份 `BASE_PRICE`。
- 权益只抵扣 `BASE_PRICE`，不抵扣 `PREBOOKING_FEE`。
- 业务枚举 `ENTITLEMENT_DEDUCTION` 在响应中按 `strategy=ENTITLEMENT` 核对。

### payment.price

- `originalAmount = BASE_PRICE正向金额合计 + 用户承担的PREBOOKING_FEE正向金额合计`。
- `discountAmount = abs(ENTITLEMENT deductions金额合计)`。
- `payableAmount = originalAmount - discountAmount`。
- 同时核对接口返回 `currency` 与 SaaS 算价结果一致。

## 5. 现金 / 权益支付生命周期（二者 payment 预期相同）

**现金支付**与**权益支付**共用本节：Preview / Create / Detail 均返回完整 `payment` 金额模块（`price` / `charges` / `deductions` 按 SaaS），并按 `payableAmount` 与权益抵扣结果分支；**不再**对权益支付单独断言 `price/charges/deductions=null` 或 Preview 全程 `NO_PAYMENT_REQUIRED`。

差异仅在**商品选择入参**（见 §6），不在 payment 返回形态。

### Preview

- 成功场景返回 `payment`。
- `payment.status=null`。
- `timeline=null`。
- `price/charges/deductions` 按配置、人数及权益使用数返回。
- 必须执行三条金额恒等式：
  - `BASE_PRICE + PREBOOKING_FEE = originalAmount`。
  - `abs(ENTITLEMENT deductions) = discountAmount`。
  - `originalAmount - discountAmount = payableAmount`。

### Create

- `payableAmount > 0`：
  - `payment.status=PENDING_PAYMENT`。
  - `timeline` 为对象，但内部时间字段均为 `null`。
  - 订单进入待支付状态，当前用例按 `order.status=9` 核对。
- `payableAmount = 0`（含权益足额抵扣到 0 元）：
  - `payment.status=NO_PAYMENT_REQUIRED`。
  - `timeline=null`（若 Apifox/SaaS 对「权益抵扣 0 元」另有 `timeline={ paidAt:null, refundedAt:null }` 约定，以对拍脚本为准，pytest 与之对齐）。
  - 不拉起收银台。

### Order Detail

- 未支付：`PENDING_PAYMENT`。
- 已授权：`AUTHORIZED`。
- 支付成功：`CAPTURED`。
- 已取消：`CANCELLED`。
- 支付失败：`FAILED`。
- 已退款：`REFUNDED`，并核对 `authorizedAt`、`paidAt`、`refundedAt`。
- 0元订单及其取消后：
  - `payment.status=NO_PAYMENT_REQUIRED`。
  - `timeline=null`（同上，权益抵扣 0 元细节与对拍脚本对齐）。
  - 必须严格区分 `null` 和 `{}`，不得把空对象当作正确结果。
- 金额模块：`price/charges/deductions` 仍按 SaaS 返回并执行三条恒等式（与 Preview/Create 成功现金路径相同），不得因「权益支付商品」而期望为 `null`。

### 发起支付

- 仍有应付金额：`POST /v2/orders/payments` 返回有效支付动作，例如 `paymentAction.type=REDIRECT` 和收银台链接。
- 无需支付（`payableAmount=0`）：按已有用例核对 `errCode=500.000.802` 和 `Payment is not required for the specified order.`。

## 6. 权益支付入参识别与客户预收费

### 权益支付（payment 预期见 §5）

- **payment 断言**：与现金相同，直接复用 §5；勿再写「Preview 金额全 null / 三阶段均为 `NO_PAYMENT_REQUIRED`」旧预期。
- 典型权益足额场景：`payableAmount=0`，Create/Detail 走 §5 的 0 元分支；Preview 仍为 `status=null` 且返回金额明细 + C-1～C-3。
- E-pass 纯权益支付的请求识别规则：`cashPaymentApplied=true`，但不传 `cashier.paymentMode=CLIENT_COLLECT`。
- 上述 E-pass 请求必须选择权益支付商品，不得因 `cashPaymentApplied=true` 误选客户预收费或现金商品。
- Membership 纯权益：`cashPaymentApplied=false`（且不传现金收银组合）。
- 纯权益且 `payableAmount=0` 时不得生成有效现金支付动作；调用支付接口时按“当前订单无需支付”的既有契约处理。

### 客户预收费

- 请求识别条件：
  - `cashPaymentApplied=true`。
  - `cashier.paymentMode=CLIENT_COLLECT`。
- Preview、Create、Detail 均为 `payment.status=NO_PAYMENT_REQUIRED`。
- `timeline=null`。
- Preview 中 `price=null`、`charges=null`、`deductions=null`。
- Create、Detail 的金额模块按 SaaS 实际返回。
- 账务金额仍按 `BASE_PRICE`、预约费承担方和权益抵扣规则计算，并核对到已有账务或交易字段，不能错误写入 Preview 中为 `null` 的金额模块。
- Apifox 使用客户预收费专用脚本，不与按 `payableAmount` 分支的通用 payment 脚本混用。
- 对 E-pass 而言，只有显式传入 `cashier.paymentMode=CLIENT_COLLECT` 才能按客户预收费识别；不能只依据 `cashPaymentApplied=true` 判断。

## 6A. 国内网点同步异步规则

- 国内网点以 `countryOrRegion=CN` 或系统等价区域标识准备数据。
- 国内网点没有同步、异步业务分支差异。
- 同一订单链路应参数化覆盖：
  - 不传 `async`。
  - `"async": false`。
  - `"async": true`。
- 三种请求的商品选择、权益校验、支付方式、订单状态和错误处理应保持一致。
- `"async": true` 不得导致国内网点必须等待异步回调或轮询后才能获得订单结果。
- 对比响应时排除订单号、请求ID和时间等动态字段，只比较核心业务语义。
- 非国内网点的同步异步行为本次未确认，不应套用国内规则。

## 6B. Bundle订单支付方式

- Bundle订单只支持权益支付语义。
- Bundle纯权益正向用例：
  - 不传 `cashier.paymentMode=CLIENT_COLLECT`。
  - Preview和Create成功。
  - 各子项权益扣减正确。
  - 整单不生成客户预收费；不拉起需付现收银台（通常 `payableAmount=0`）。
  - `payment` 预期与 §5 现金/权益一致：Preview `status=null` 且返回金额明细并做 C-1～C-3；Create/Detail 按 `payableAmount`（足额抵扣时为 `NO_PAYMENT_REQUIRED`）分支，**不**再断言 Preview 金额模块为 `null`。
- Bundle现金用例（**后端忽略入参，不报错**）：
  - 传入现金支付组合，例如 `cashPaymentApplied=false`、`cashier.paymentMode=DP_COLLECT`。
  - 后端**忽略**现金相关入参，**不返回业务错误**。
  - 按权益支付语义成功创单（与纯权益正向一致），不按现金商品选择收银台。
  - 自动化断言：Create 业务成功（`code=0`），而非 `ftPayAssertBusinessRejected`。
- Bundle客户预收费负向用例：
  - 传入 `cashPaymentApplied=true`、`cashier.paymentMode=CLIENT_COLLECT`。
  - Create（或 Preview，若有）返回业务错误，不选择客户预收费商品。
  - 不生成订单，不扣减权益，不生成预收费交易。
- Bundle不支持支付方式的错误码和提示尚未确认，自动化参数暂记为待确认，禁止补造。

## 7. 错误场景自动化规则

- 场景1、场景4、场景6直接参数化为错误用例。
- 测试到 Preview 为止：
  - HTTP和业务响应符合接口约定。
  - 断言已确认的业务错误码和提示。
  - 不读取有效 `payment.price/charges/deductions`。
  - 不调用 Create 和支付接口。
- “不支持权益抵扣但请求使用权益”的用例同样走业务错误分支。
- 未经需求、接口文档或现有用例确认的错误码必须标为待确认，不能在自动化中补造。

## 8. 推荐的 pytest 落地方式

- 在 `api-testcases/api_tests/services/` 复用或扩展订单HTTP封装、payload构造和 payment 公共断言。
- 在 `api-testcases/api_tests/scenarios/` 提供单一主链路编排入口，例如 `RunPrebookingPaymentMainE2EScenario`。
- 主 E2E 测试函数只调用编排入口；负向、边界和单接口用例可直接调用原子级 `Post*`、`Assert*`。
- 对外函数使用 PascalCase，并明确返回类型。
- 可复用 `Assert*` 必须通过 `papi2548_helpers._RunAllureAssertionStep` 上报断言结果。
- 建议拆分公共断言：
  - `AssertPaymentPriceSummary`。
  - `AssertPaymentStageStatus`。
  - `AssertPaymentTimeline`。
  - `AssertBasePriceDetails`。
  - `AssertPrebookingFeeDetails`。
  - `AssertEntitlementDeductions`。
  - `AssertBusinessError`。
  - `AssertEpassPureEntitlementSelection`。
  - `AssertDomesticAsyncEquivalent`。
  - `AssertBundleEntitlementOnly`。
- 场景配置建议使用不可变 `dataclass`；测试使用参数化矩阵，避免为七种配置复制七套断言代码。
- 测试数据优先由 session fixture 自动准备；BOSS、SaaS 暂时无法自动配置时，允许使用环境变量或 JSON 覆盖，但需明确跳过原因和数据依赖。

## 9. 建议的自动化主链路

鉴权由 `Token` fixture 提供，不计入主场景步骤：

1. 准备或解析会籍、权益和预约商品。
2. 应用对应的 BOSS 付费方式、预约价和超人次价。
3. 按用例设置普通订单或Bundle订单，并设置国内网点的`async`参数。
4. 查询 SaaS 价格，保存原始价格响应作为断言基准。
5. 调用 Preview。
6. 断言业务成功或业务错误。
7. 成功场景断言 payment 状态、timeline、charges、deductions 和价格恒等式。
8. 允许创建时调用 Create。
9. 查询 Order Detail，断言待支付或无需支付状态。
10. 需支付场景调用支付接口并核对支付动作。
11. 按用例需要继续模拟授权、支付成功、取消、失败或退款，再查询 Detail。

Allure 中的 `S01/S02/...` 应由 `AllureHttpScenarioSteps.Next` 按实际HTTP请求递增，不要写死固定编号。

## 11. 已知数据问题和实现注意事项

- 原测试分析中存在标题写“使用权益点数2”，但实际请求参数为1的情况；自动化必须以请求体真实参数为计算依据，并单独记录文档问题。
- 原文中可能仍保留早期示例数值；以每条用例下的“补充预期（本次确认，以此为准）”、`pc` 中“核对配置（本次确认）”及“数据”节点为准。
- 不使用响应全文完全相等断言；应断言核心结构、金额关系、状态和关键业务语义，避免兼容性新增字段导致误报。
- `timeline=null`、空对象和“对象存在但内部字段均为null”是三种不同语义，必须分别断言。
- Membership 与 E-pass 的字段路径或请求参数可以不同，但七种配置、金额计算和 payment 生命周期应复用同一语义层断言。
- **权益支付与现金支付的 payment 返回预期已对齐**（见 §5）；仅客户预收费仍走 Preview 金额模块为 `null`、三阶段 `NO_PAYMENT_REQUIRED` 的专用分支。
- E-pass中 `cashPaymentApplied=true` 不能单独作为客户预收费判据；必须同时检查是否显式传入 `CLIENT_COLLECT`。
- 国内网点的 `async=true` 是兼容入参，不代表切换到另一套异步业务流程。
- Bundle只允许权益支付语义：现金入参被忽略且不报错；客户预收费应在 Create/Preview 阶段拒绝且无订单、权益、账务副作用。

## 12. 实现完成后的最低校验

- 七种配置场景均有用例映射。
- Membership、E-pass 均覆盖。
- Lounge、Fast Track 均覆盖或证明共用参数化用例。
- 权益数0、1、3均覆盖。
- 现金、权益支付、客户预收费均覆盖。
- 权益支付与现金共用 §5 payment 断言（含金额明细与 C-1～C-3）；客户预收费仍用专用 null 金额分支。
- E-pass纯权益覆盖`cashPaymentApplied=true`且不传`CLIENT_COLLECT`。
- 国内网点覆盖`async`缺失、`false`、`true`并验证核心结果等价。
- Bundle覆盖权益支付成功（payment 同 §5）、现金入参忽略不报错、客户预收费被拒绝。
- 场景1、4、6及“不支持权益抵扣”负向用例均不会继续执行 Create。
- Preview、Create、Detail 的 `payment.status` 和 `timeline` 分阶段断言。
- 三条价格恒等式使用 `Decimal` 校验（现金与权益支付成功路径均执行）。
- 0元订单 Detail 严格断言 `timeline is None`（或与对拍脚本的权益抵扣 0 元 timeline 约定一致）。
- pytest、Allure和Apifox/Postman断言语义保持一致。
