# 会籍权益分级需求文档 - 测试分析点

> 说明：本文件仅提炼测试分析点，用于指导后续按《功能测试用例设计规范（含优先级体系）》编写具体用例（含用例ID、步骤、预期等）。

## 一、会籍注册接口 `/v2/memberships`（scopeType 生成）

### 测试分析点

1. **正向功能验证**
   - scopeType 计算正确：  
     - 同一品类下所有权益均未勾选 `tier` → `scopeType=1 (GLOBAL)`。  
     - 同一品类下存在至少一个权益勾选了 `tier`（无论分组是否相同）→ `scopeType=2 (TIERED)`。  
   - 不同品类各自独立计算 scopeType，互不干扰。

2. **规则验证（scopeType 判定规则的等价类/判定表）**
   - 等价类拆分：  
     - 模板中该品类**无任何权益**。  
     - 有权益，但**无任一权益关联分组 / tier 未勾选**。  
     - 有权益，**至少一个权益勾选 tier 且 BOSS 分组存在 label**。  
     - 有权益，勾选了 tier，但 **BOSS 分组缺少 label / 配置异常**（预期兜底策略）。  
   - 多权益组合：  
     - 同一品类下多个权益都勾选了同一 tier 分组。  
     - 同一品类下不同权益勾选了不同 tier 分组。  
   - 与 SAAS 权益模板、BOSS 分组 label 的数据联动：  
     - SAAS 模板关联的分组 ID 正常存在于 BOSS，并能查到 label。  
     - SAAS 模板关联的分组 ID 不存在或已删除时的处理。

3. **边界值验证**
   - 该品类下权益数量的边界：0 条、1 条、多条。  
   - 勾选 tier 的权益数量：0 条、1 条、多条。  
   - 分组 ID / label 为空、长度边界、特殊字符（保障调用 BOSS 查询的健壮性）。

4. **异常场景验证**
   - SAAS 模板配置不完整：  
     - 模板中勾选了 tier，但 BOSS 查不到对应分组或 label。  
   - SAAS 模板与 BOSS 配置不一致引发的容错：  
     - scopeType 无法准确判断时，是否有兜底策略（例如回退为 GLOBAL 或直接报错）。  
   - 会籍注册失败时的返回结构与错误码（是否受新增 scopeType 的影响）。

5. **接口/系统集成验证**
   - 与 SAAS 模板服务、BOSS 分组服务的集成：  
     - 会籍注册时对分组/label 的读取是否只在后台逻辑中完成，不影响接口性能与稳定性。  
   - 注册接口生成的 `scopeType` 是否能被后续 `/v2/entitlements/search`、`/v2/entitlements/details` 正确识别与复用。

6. **数据状态验证**
   - 会籍在数据库中保存的 `scopeType` 与计算逻辑一致（包括历史会籍与新增会籍）。  
   - 会籍模板变更 `tier` 配置后，已注册会籍的 `scopeType` 是否/如何更新（若有设计要求则需覆盖）。

## 二、权益查询接口 `/v2/entitlements/search`

### 测试分析点

1. **正向功能验证**
   - `scopeType=1 (GLOBAL)` 时：  
     - 返回结构与旧逻辑完全一致，`details` 中六个字段（含 `allowedGuestsPerUsage`、其他 4 个权益字段）正常返回。  
     - `maxGuestsNextUse` 按原规则正常计算。  
   - `scopeType=2 (TIERED)` 时：  
     - 返回**同类型权益的总和**，而非按 tier 拆分明细。  
     - `maxGuestsNextUse` 通过 SAAS 权益里的网络分组 ID 到 BOSS 查找 `label` 并正确展示。  
     - `allowedGuestsPerUsage` 返回 `null`。  
     - 其他 4 个字段返回 `null`，总计通过汇总字段体现。

2. **规则验证（GLOBAL vs TIERED 行为差异）**
   - GLOBAL 客户：  
     - `scopeType=1`，各字段行为与历史版本保持完全一致（回归验证）。  
   - TIERED 客户：  
     - `scopeType=2`，验证：  
       - 只返回总和，不暴露各 tier 明细。  
       - 总和数据与 `/v2/entitlements/details` 中各 tier 汇总结果一致。  
       - `maxGuestsNextUse` 与 BOSS `label` 对应关系正确。
   - 跨 module（品类）组合场景：  
     - 一个会籍在 module=1 为 GLOBAL，module=2 为 TIERED → 各模块返回各自正确的 scopeType 与数据形态。

3. **边界值验证**
   - 权益点数（各字段）的边界：0、1、系统上限、非法负数（应通过数据写入防线避免）。  
   - TIERED 客户中某些 tier 无权益（0 点）时：  
     - 总和计算是否正确处理 0 值。  
   - `maxGuestsNextUse` 在无共享点、无买点、仅部分字段有值时的组合边界。

4. **异常场景验证**
   - 会籍不存在或已失效时的返回。  
   - 传入的 module 不存在或未在会籍中配置时（与 `/details` 的 500.030.029 一致性）。  
   - BOSS 返回异常（无法获取分组或 label）时，对 `scopeType` 和返回字段的容错策略。  
   - 对 TIERED 客户误期望明细的调用场景（接口本身只返回汇总，但需验证说明文档与行为一致）。

5. **接口/系统集成验证**
   - `/v2/entitlements/search` 与：  
     - `/v2/entitlements/details` 的数据一致性（TIERED 客户：search 的总和 = details 按 tier 汇总）。  
     - BOSS 资源分组与 label 的联动正确，且性能可接受。

6. **数据状态验证**
   - 权益被编辑（调用 `/v2/entitlements/update`）后，再次调用 `/v2/entitlements/search`：  
     - 汇总字段、`scopeType` 等是否实时更新且一致。  
   - 旧数据迁移到新增 scopeType 体系后，历史会籍的 search 返回是否正确。

## 三、权益明细接口 `/v2/entitlements/details`

### 测试分析点

1. **正向功能验证**
   - 通用返回结构：  
     - 任意 scopeType（1 或 2）调用，均返回 `membershipId`、`module`、`scopeType` + `entitlements`。  
   - `scopeType=1 (GLOBAL)`：  
     - 返回结构与 `/search` 完全一致（一组明细对象，包含 6 个字段）。  
   - `scopeType=2 (TIERED)`：  
     - `entitlements` 为数组，按 `tier` 维度拆分，每个元素包含 `tier` 与 `details` 结构。

2. **规则验证**
   - 仅支持**单品类查询**：  
     - 每次请求只能指定一个 module，传多个时的处理（拒绝/只取一个的规则）。  
   - 无该品类数据时：  
     - 返回提示语/错误码行为与需求一致（结合 500.030.029 和 500.030.007 的使用场景）。  
   - TIERED 权益：  
     - 所有已配置的 tier 都有对应明细记录。  
     - 各 tier 的点数之和 = `/v2/entitlements/search` 中的总和（对 TIERED 客户尤为关键）。

3. **边界值验证**
   - module 的边界值：  
     - 非法 module（0、负数、不存在的 ID），触发 500.030.029。  
   - TIER 列表边界：  
     - 无 tier（GLOBAL）、1 个 tier、多级 tier。  
   - 权益字段（点数、allowedGuestsPerUsage 等）的边界值同 `/search`。

4. **异常场景验证**
   - 500.030.029：  
     - 会籍存在，但请求的 module 不存在。  
   - 500.030.007（兜底）：  
     - 后端无法从相关服务获取权益明细时触发（网络问题、服务异常等）。  
   - 请求参数不合法（缺失 membershipId/module、格式错误）时的错误处理。

5. **接口/系统集成验证**
   - 与 `/v2/entitlements/search` 的协同：  
     - 对于 TIERED 客户，通过 details 能补足 search 不返回的各等级明细。  
   - 与 BOSS/SAAS 权益模板的对应：  
     - 每个 tier 在 BOSS/模板中存在合法配置，details 返回与配置一致。

6. **数据状态验证**
   - 编辑权益后（通过 `/v2/entitlements/update`）再查 `/details`：  
     - 对应 tier 的明细是否正确变化。  
     - 汇总是否与 `/search` 保持一致。

## 四、编辑权益接口 `/v2/entitlements/update`（新增 `tier` 字段与规则）

### 测试分析点

1. **正向功能验证**
   - GLOBAL 会籍（scopeType=1）：  
     - 不传 `tier` 也能正常编辑整体权益（兼容旧逻辑）。  
   - TIERED 会籍（scopeType=2）：  
     - 传入合法的 `tier` 且该 tier 存在对应权益模板时，编辑成功。  
     - 返回数据结构与 `/v2/entitlements/search` 一致，包含更新后的总数与 `scopeType`。

2. **规则验证（四类错误码 + 特殊情况）**
   - 无分级权益却传了 `tier` → 500.030.026：  
     - `Operation not allowed. Tiered entitlements are not enabled.`  
   - 存在分级权益却未传 `tier` → 500.030.027：  
     - `Tiered entitlements are enabled. Please specify the tier to be updated.`  
   - 操作不存在的 `tier` → 500.030.028：  
     - `The specified tier does not exist.`  
   - 特殊情况：  
     - 未配置 `tier1`（默认兜底），却尝试操作 `tier1` → 同样 500.030.028。  
     - 指定的 `tier` 没有对应的权益模板（买点、大客户等） → 返回兜底提示（与 500.030.007/其他兜底逻辑的关系）。  

3. **边界值验证**
   - `tier` 的边界：  
     - 最小 tier（1）、最大合法 tier、超出范围的 tier（0、负数、极大值）。  
   - 点数编辑边界（quantity / purchasedQuantity）：  
     - 0、最大允许值、超上限、减到负数（应触发已有的余额不足类错误码，如 500.030.012 等）。  
   - 同时携带多个字段时的组合：  
     - 仅修改 `usageRestriction`；  
     - 仅修改 `quantity`；  
     - 仅修改 `purchasedQuantity`；  
     - 同时修改多个字段但满足规则的合法组合。

4. **异常场景验证**
   - TIERED 会籍中**同时传 `quantity` 和 `purchasedQuantity`** 等已有限制规则是否仍然生效（与原买点规则文档的一致性）。  
   - 缺失 membershipId / module / tier / 必要字段时，接口的参数校验错误码与提示。  
   - 更新失败场景下，数据必须保持不变（幂等与事务性）。

5. **接口/系统集成验证**
   - `/update` 执行成功后：  
     - 立即调用 `/v2/entitlements/search` 与 `/v2/entitlements/details`，验证：  
       - 总数和分级明细均更新正确。  
       - scopeType 未被错误修改。  
   - 与 BOSS/SAAS 模板的耦合：  
     - 对不存在模板的 tier 请求更新时，是否按兜底策略报错而非静默失败。

6. **数据状态验证**
   - 多次更新同一个 tier 的累积效果是否正确（加点、减点、设置为 0）。  
   - 在 GLOBAL → TIERED 转换或配置变更场景下（如果允许），已有数据的兼容性与更新行为。

## 五、资源查询接口 `/v2/resources`（tier 字段改造）

### 测试分析点

1. **正向功能验证**
   - 不传 `tier` 查询：  
     - 返回 BPN 项目级数据，与旧行为一致。  
   - 传入 `tier` 查询：  
     - 使用「网络分组 ID + 项目 ID」进行查询，返回与分组等级对应的资源数据。  
   - `tier` 字段不再写死为 1，而是**动态读取 BOSS 网络分组的 tier 值**。

2. **规则验证**
   - 资源分级对资源范围的影响：  
     - 即使权益进行了分组，总资源范围保持不变，仅资源中的 `tier` 字段发生变化。  
   - `tier` 与 BOSS 网络分组的一致性：  
     - 同一资源在不同分组中具有不同 tier 值时，查询结果是否正确反映。  
   - 未配置分组/未分级的资源：  
     - `tier` 应为默认值（如 1 或 null，视具体设计而定），并与文档约定一致。

3. **边界值验证**
   - `tier` 的取值边界：1、最大等级、非法等级（0、负数、超最大）。  
   - 资源 ID、项目 ID 的边界（存在/不存在、已下线资源）。

4. **异常场景验证**
   - 传入不存在的 `tier` 与项目组合时的行为（无数据 / 错误提示）。  
   - BOSS 侧网络分组数据异常或缺失时，资源查询的容错策略。  

5. **接口/系统集成验证**
   - 与 BOSS 项目、价格清单数据源的一致性：  
     - 资源信息（价格、等级等）在 BOSS 变更后是否按预期体现在 `/v2/resources` 中。  
   - 与权益模板的联动：  
     - 权益分组调整后，`/v2/resources` 返回中的 `tier` 是否同步更新。

6. **数据状态验证**
   - 分级前后的资源数据对比：  
     - 分级前后，资源总量与可用范围不变，仅 `tier` 信息调整。  
   - 多分组资源在不同 `tier` 查询下的表现。

## 六、告警机制

### 测试分析点

1. **正向功能验证**
   - 资源多分组告警：  
     - 某个资源同时存在于 ≥2 个分组 → 触发告警，记录资源 ID、分组列表、项目 ID 等关键信息。  
   - 资源等级不完整告警：  
     - 某项目下只要有资源配置了等级，则该项目下所有资源在各等级上都应完整；  
     - 若有资源缺失某个等级分组 → 触发告警。

2. **规则验证**
   - 告警判定条件的等价类：  
     - 所有资源只在一个分组且等级完整 → 不触发告警。  
     - 部分资源在多个分组 → 仅触发「多分组告警」。  
     - 部分资源缺少某个等级分组 → 仅触发「等级不完整告警」。  
     - 同时存在多分组 + 等级不完整 → 验证是否**两种告警都触发**以及记录内容是否区分。  

3. **边界值验证**
   - 分组数量边界：0、1、2、N 个分组。  
   - 等级边界：只有一级、两级、多级等级；缺失首级（tier1）、中间级（tier2）或最高级。

4. **异常场景验证**
   - BOSS 分组数据不完整或脏数据导致「误告警 / 漏告警」的情况，系统是否有兜底或监控。  
   - 告警服务自身异常时的处理（不会影响主业务接口）。  

5. **接口/系统集成验证**
   - 告警机制与：  
     - BOSS 分组配置、SAAS 权益模板、`/v2/resources` 查询结果之间的数据一致性。  
   - 告警输出的渠道和格式（日志、监控平台、邮件等，如有要求需覆盖）。

6. **数据状态验证**
   - 配置修复后的再验证：  
     - 修复资源分组或等级配置后，告警是否自动消失或被标记为已恢复。  
   - 历史告警记录的可追溯性（是否能回溯到当时的配置状态）。
