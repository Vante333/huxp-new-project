# 资源缓存与可用性缺陷回归测试用例

## 测试范围说明

- rc: 基于代码评审缺陷清单（FastTrack/LocalOffer/Dining/Lounge 缓存、可用性校验、RequestContext、CountryRegion）；用于修复后回归与上线前验证。
- rc: 覆盖缓存刷新 Job（ResourceRefreshCacheJob / CacheCleanJob）后详情一致性、Dining 可用性双模块、非 HTTP 链路上下文、下游空值/失败、CountryRegion 映射。
- rc: 语言仍走 query/body `language`（非 Accept-Language）；同 `resourceId` 不同语言缓存不串语言——本表不单测语言串扰，仅在多语言刷新场景抽样。
- rc: 下游失败是「业务降级」还是「500」以产品/研发确认口径为准；未确认前预期标注「待需求确认」。
- rc: 不覆盖支付下单主链路、非本清单品类无关字段全量对拍。

## FastTrackL1缓存刷新（FastTrackDetailCacheRefresh）

### tc-p1: FastTrack刷新后L1不再命中旧详情

- pc: 准备可访问的 FastTrack `resourceId`；先 `GET` 详情记下基线字段（如名称/坐标/更新时间相关可观察字段）；具备触发 `ResourceRefreshCacheJob` 或等价 `refreshDetail` 的权限；可在 BOSS/源侧改一处可观察字段后刷新。
- 调用详情接口拿到旧响应并确认可缓存命中。
  - 接口成功，记录关键字段快照 A。
- 修改源数据为可区分新值，触发 FastTrack `refreshDetail`（Job 或运维入口）。
  - 刷新任务成功完成，无失败重试堆积。
- 在 L1 TTL 窗口内（约 55 分钟内）再次 `GET` 同一 `resourceId`+同一 `language` 详情。
  - 返回新值，不等于快照 A；不得仍返回刷新前旧数据。
- rc: 缺陷根因：refresh 使用 `API:FasTrackDetail:`，读路径为 `API:FastTrackDetail:`。
- tag: cache,L1,FastTrack,P1

### tc-p2: FastTrack不同language刷新互不影响

- pc: 同一 `resourceId` 支持至少两种 `language`（如 en、zh-CN）。
- 分别缓存两种语言详情后，仅刷新其中一种语言。
  - 被刷新语言拿到新数据；另一语言仍为该语言正确内容，不串语言、不误清。
- tag: cache,language,FastTrack

## LocalOfferL2缓存刷新（LocalOfferDetailCacheRefresh）

### tc-p1: LocalOffer刷新后L1miss时L2读到新数据

- pc: 准备 LocalOffer `resourceId`；可触发 `refreshDetail`；可制造 L1 miss（重启实例 / 等 L1 过期 / 清 L1，按环境能力选一）。
- 先读详情形成 L2 旧数据，记录快照 A；改源数据后执行 refresh。
  - refresh 成功。
- 确保 L1 miss 后再次 `GET` 详情（同 `projectId`+`resourceId`+`language`）。
  - 返回刷新后新数据，不等于 A；不得仍命中旧 `LocalOfferDetail:` 前缀 Redis 数据。
- rc: 缺陷根因：`@DataCacheable` 用 `LocalOfferDetail:`，`@DataCachePut`/L1 用 `API:LocalOfferDetail:`。
- tag: cache,L2,LocalOffer,P1

## DiningL2缓存刷新（DiningDetailCacheRefresh）

### tc-p1: Dining刷新后详情读到新数据而非旧RDetail

- pc: 准备 Dining 资源；可触发 DiningCache.refreshDetail（预热/刷新 Job）；可改源侧可观察字段。
- 读详情记快照 A → 改源数据 → 执行 refresh → 再读详情（必要时制造 L1 miss）。
  - 二次读取为新数据；不得长期停留在旧 `RDetail:` 对应内容。
- rc: 缺陷根因：Put=`RDetail:`，Get=`RDetailV2:`。
- tag: cache,L2,Dining,P1

## Dining可用性双模块（DiningCheckResourcesAvailable）

  - 该合法套餐资源不被判无权限；详情不为 null、列表包含该资源（与旧双模块逻辑一致）。

  - 合法券类资源通过可用性校验，不被过滤为无权限。
- tag: Dining,availability,needFilter,P1

### tc-p2: 确无SET_MEAL与COUPON权限的餐饮资源被正确过滤

## RequestContext与非HTTP链路（RequestContextNullGuard）

### tc-p2: 非HTTP未init上下文时网点列表或可用性不NPE

- pc: 构造未调用 `requestService.init()` 的调用链（MQ/异步/内部调用，按环境可测入口）；或在 Job 中故意不传/不 init program 上下文（若可安全演练）。
- 触发依赖 `getAvailableCodes` / `checkResourcesAvailable` 的逻辑。
  - 不出现 `RequestContext` NPE 导致进程级未处理异常；表现为明确业务错误、跳过或约定降级（具体码「待需求确认」）。
- rc: 对比：ResourceRefreshCacheJob、CacheCleanJobService 已有 init，说明上下文依赖已知。
- tag: RequestContext,async,P2

### tc-p1: HTTP正常请求下资源列表与权限过滤仍可用

- pc: 标准 HTTP 已 init 上下文；Lounge/FT/Fitness/Esim/LocalOffer 任选高频品类。
- 调用资源列表及需可用性过滤的详情。
  - 正常返回；`programId` 正确传递，无因上下文缺失失败。
- tag: RequestContext,smoke,P1

## available空值与下游失败（AvailabilityNullAndDownstreamFailure）

### tc-p2: verifyAvailability返回available为null时不NPE

- pc: 可 mock/挡板 basedata network 或 transportHub，使成功响应但 `available` 缺失/null（若环境具备）。
- 触发 TransportHub 校验或 `getResourceDetailCache` 权限过滤。
  - 不 NPE/500（因拆箱）；按约定视为不可用或降级（「待需求确认」）。
- tag: NPE,Boolean,P2

### tc-p2: basedata失败时资源列表行为符合约定

- pc: 模拟 getModuleNetwork / verifyAvailability 超时、5xx 或 data=null；对比 NetworkResources 失败返回 empty 的分支。
- 调用依赖 `getAvailableCodes` 的资源列表，及订单侧 `checkResources` / `findInvalidResourceIds` / MultiOrder 餐饮休息室校验（抽样）。
  - 行为符合产品确认：降级为空列表/判无权限 **或** 明确 5xx；不得静默返回未过滤脏全量；与「旧逻辑清单未命中返回 false」对比无意外放行。
- rc: 预期口径待产品确认（降级 vs 失败快）。
- tag: downstream,degrade,P2
