# 功能测试用例设计（含优先级）

## 触发条件

用户涉及 **功能测试用例** / **testcases** / **用例优先级（P1、P2、P3）** / **XMind 或脑图导入** / **XMind 转 Markdown、脑图同步、用 xmind 替换 md** / **tc-p1、tc-p2、tc-p3** / **需求拆解测试点**，或明确提出 **接口契约模式** / **接口测试用例** / **API 用例** / **根据 Apifox 接口文档生成字段级用例** / **接口入参与响应字段细化到具体值** / **api-automation-ready** 时，应先 **Read 本文件**，再按需 **Read [reference.md](reference.md)**（完整规范、示例与附录）。

若同时在搭建 **pytest 接口自动化** 或 **api-testcases**，另见 [api-testcase-pack](../api-testcase-pack/SKILL.md)。

## 用例生成模式（先判定，条件启用）

1. **通用功能模式（默认）**：页面、流程、配置、权限、消息、定时任务及其他非接口需求沿用现有工作流；不要求 Method、Path、endpointId、请求 Body 或 Apifox 文档。
2. **接口契约模式（显式或语义触发）**：用户明确说“接口契约模式”，或明确要求结合 API/Apifox 契约生成接口用例时启用。只因需求正文背景中出现“接口”二字，不得误触发。
3. **混合模式**：同一需求同时含页面与 API 时按模块/用例分别判断；仅接口用例叠加字段级契约规则，非接口用例不得因缺少 endpointId 或 Body 被标记阻塞。

接口契约模式当前只生成**后续可转自动化脚本的测试用例**；除非用户另行要求，不生成 `pm.test`、前后置脚本、pytest 代码，不创建或同步 Apifox 场景。

## 用例文件纯净输出（强制）

落盘到`testcases/**/*.md`的文件默认只保留：

1. 一个H1文档标题；
2. 按业务或接口划分的模块标题；
3. `tc:`或`tc-p1/tc-p2/tc-p3:`用例及其`pc/步骤→预期/rc/tag`子节点。

禁止输出独立的全局分析章节，包括但不限于：`测试范围说明`、`需求原子化`、`需求事实与范围`、`测试模型`、`契约冲突与自动化阻塞项`、`共性测试数据`、`覆盖追溯`、`执行与自动化门禁`。需求拆解、冲突分析、数据建模和追溯关系仍须在设计过程中完成，但只作为Agent内部工作产物，不写入用例文件。

每条用例必须自包含：所需测试数据及来源写入该用例`pc:`，需求/契约冲突、待确认项、自动化阻塞原因写入该用例`rc:`；不得依赖全局公共表解释变量或预期。用户明确要求单独输出分析文档时，另建分析文件，不与测试用例混写。

## 强制工作流

输出或改写用例前，读取 [reference.md](reference.md) 中与任务相关的章节，并依次执行：

1. **确认输入与范围**
   - 读取需求正文、原型/接口定义、业务规则、历史用例及用户指定输出文件。
   - 明确本次新增、修改、不变、明确不测及上下游依赖；不要把背景描述误当作需求。
2. **解析接口契约（仅接口契约模式）**
   - 优先从用户给出的 Apifox URL 识别 projectId、endpointId、branchId；必要时用只读 CLI `endpoint list/get` 按 **Method + 标准化 Path** 唯一定位接口。
   - 对请求/响应中的 `$ref` 继续用 `schema get` 递归解析，直至得到 Header、Path、Query、Body 与响应字段的类型、必填性、格式、枚举、长度和 null 约束；未解析完成不得声称契约完整。
   - 需求定义业务行为与业务预期，Apifox 定义接口结构；示例值只辅助理解，不自动成为环境测试数据或业务预期。来源冲突须记录，禁止静默择一。
3. **需求原子化**
   - 按“触发条件 → 操作/处理 → 预期结果 → 约束”拆成可验证的需求点并编号 `R-001...`。
   - 覆盖功能、字段、业务规则、流程、状态、权限、时间、数据一致性、错误处理和非功能约束。
   - 原子需求表仅用于内部设计与反查，不写入`testcases/**/*.md`。
4. **深挖隐含需求**
   - 从用户目标、上下游契约、历史兼容、重复提交、并发、回滚、审计及失败恢复反推遗漏测试点。
   - **事实、合理假设、待确认项必须分开**；不得把推测写成已确认预期。假设需说明依据和风险。
5. **建立测试模型**
   - 流程类：基本流、备选流、异常流、恢复流。
   - 状态类：合法迁移、非法迁移、重复迁移、终态、并发迁移。
   - 规则类：判定表；组合过多时先约束组合，再用成对/正交覆盖。
   - 输入类：有效/无效等价类、边界内外值、空值、类型/格式、特殊字符。
6. **从用户视角补全场景**
   - 覆盖首次/重复/高频操作、误操作、取消/返回/刷新/重试、中断后继续，以及结果反馈是否清晰。
   - 同时验证用户可见结果、接口/数据落库、副作用、上下游一致性和失败后的数据不变性。
7. **字段级接口用例设计（仅接口契约模式）**
   - 每个请求字段写明完整路径、具体字面值或变量、数据类型、来源和选择原因；动态值必须指明来自数据集、环境、鉴权响应、前序步骤或运行时生成。
   - 对所有响应字段给出处理结论：固定值、与请求/前置值一致、业务公式、结构/类型校验，或“本用例不校验 + 原因”；关键字段应拆成独立步骤，便于后续脚本定位失败。
   - 金额、数量、状态等预期不得由同一被测响应反向生成；前置基准值须来自受控测试数据、独立查询或已确认规则。
   - **优先接口串联解决测试数据**：先尝试用同一用例或会话内的前序接口实时创建订单、支付动作、会籍等数据，并将响应变量传给后续接口；不得因已有手工ID不方便或缺少清理接口，直接把本可串联的主链路标为 blocked。
   - 串联示例：`Preview → Create → Payments → Details`；取消/退款场景可继续串联已确认的取消接口后再次查询。每一步都须写明成功判定、变量生产路径和消费者。
   - 对商品A/B、Program、券、价格基准等稳定配置使用环境变量或受控数据；根据前序路由结果选择对应变量断言，不从被测响应反推预期。
   - **默认无需清理运行时业务数据**：使用唯一 email/clientUserId、订单号等隔离每次执行时，订单、支付动作、会籍等留存数据不构成自动化阻塞，也不要求为标记 ready 强行设计删除步骤。
   - 仅当用例会修改共享配置、消耗稀缺资源、造成真实资金/权益风险，或残留数据会影响同次/后续执行时，才写明恢复、隔离或清理要求。
8. **测试点到用例**
   - 先在内部形成 `需求ID → 测试点 → 设计方法 → 用例ID/标题` 的追溯关系，再按团队格式落盘；不得输出全局追溯表。
   - 同构场景参数化合并；仅在逻辑、前置、定位价值或优先级不同的情况下拆分。
9. **质量闭环**
   - 反查每个需求点、规则分支、状态边、错误码和高风险假设是否覆盖。
   - 执行完整性、准确性、可执行性、可验证性、独立性、用户视角及去重检查。
   - 接口用例在契约唯一、字段来源完整、关键预期有依据，且测试数据可通过前序接口、环境变量或受控Setup获得时标记 `api-automation-ready`。
   - **缺少数据清理接口本身不是 blocked 理由**；若可使用唯一运行时数据并串联完成验证，应标记 ready。只有关键数据无法造出、共享配置无法受控、特殊失败分支无法注入、核心预期未确认等真实障碍，才标记 `api-automation-blocked` 并逐项写明原因。非接口用例不应用此门禁。

## 不确定需求处理

- 信息缺失但不影响主体设计：基于证据形成**暂定假设**并继续设计，同时列出待确认项。
- 不同解释会改变核心流程、资金/权益、权限或数据结果：先提出聚焦问题；未答复时保留分支用例，预期标记“待需求确认”。
- 禁止凭空补造错误码、字段值、阈值或系统行为；无法确定时描述需要验证的契约，不伪造确定结论。

## 方法选择速查

- 输入范围/格式：等价类 + 边界值。
- 多条件业务规则：判定表；组合规模较大时用成对/正交法缩减。
- 端到端操作链路：流程分析 + 场景法。
- 生命周期/状态约束：状态迁移法。
- 历史缺陷、脆弱依赖、安全与容错：错误推测法。
- 用户角色、环境、配置等多因子：分类树后使用成对/正交覆盖。

## XMind → testcases Markdown（必读，禁止手写转换器）

用户要求 **用 XMind 覆盖/替换** `testcases/**/*.md`，或 **XMind 转 Markdown 落盘** 时：

1. **禁止**新建转换脚本、禁止用 Shell 解压 `content.json` 手写解析；仓库已有工具。
2. **默认工具**：`tools/req-docs/xmind_to_testcases_md.py`（`tc-p*` 团队格式、`### tc-p1:` 层级）。细则见 [reference.md](reference.md) §8.4。
3. **直接执行**（PowerShell，路径按用户给定替换）：

```powershell
python tools/req-docs/xmind_to_testcases_md.py `
  --xmind "path/to/源.xmind" `
  --out "testcases/{迭代}/PAPI-xxxx-测试用例-001.md" `
  --requirement "requirements/{迭代}/PAPI-xxxx.md"
```

4. **转换后必查**：只保留H1、业务/接口模块和`tc-p*`用例；删除`测试范围说明`、分析表、公共数据表、追溯表及自动化门禁等全局章节。脑图未挂`tc-p*`的分析节点不应合并进用例文件。
5. **仅通用大纲**（无 `tc-p*`）时用 `tools/req-docs/xmind2md.py`；另一套 tc 结构见 `tools/req-docs/xmind_to_markdown_v2.py`（见 `tools/README.md`）。

## 核心检查清单（简版）

- **可追溯**：每个需求点有唯一 ID；每条用例至少覆盖一个需求点；待确认项和假设可定位。
- **覆盖面**：基本流、备选流、异常流、恢复流；正向、反向、边界、组合、状态、权限、并发/幂等、上下游一致性。
- **可验证**：预期结果包含可观察对象与判定标准，并核对失败后无非法副作用。
- **用户视角**：操作符合真实习惯；反馈明确；重复、取消、刷新、重试和中断恢复有覆盖。
- **优先级**：仅用 P1/P2/P3；前缀 `tc-p1:` / `tc-p2:` / `tc-p3:` 或 `tc:`；历史 P0 体系迁移规则见 [reference.md](reference.md) §2.1。
- **命名**：模块名与用例名 **无空格**；英文 **PascalCase**；接口路径作模块名时 **`/` → `_`**。
- **结构**：H1 根标题不导入系统；用例标题行 `tc:` 或 `tc-p{n}:`；子项顺序 `pc:` → 步骤（一级 `-`）→ 单条预期（子级 `  -`）→ 可选 `rc:`、`tag:`；**每步仅一个预期**。
- **纯净输出**：用例文件无测试范围、需求原子化、冲突清单、共性数据、覆盖追溯或自动化门禁等全局分析章节；数据与阻塞信息分别内嵌到对应用例`pc/rc`。
- **精简**：同构场景参数化合并；忌「逻辑与 A 一致」式重复；错误码不跨章重复（见 [reference.md](reference.md) §3.4、§9.1）。
- **落盘**：`testcases/{需求名称}-测试用例-{序号}.md`（见 [reference.md](reference.md) §5.1）。
- **接口字段（条件项）**：全部请求字段均有值/来源/类型，全部响应字段均有断言策略或不校验原因；boolean/number 不得误写为字符串。
- **接口预期（条件项）**：JSONPath、期望值/引用值/公式与依据明确；示例响应和当前实际响应不得反向覆盖需求预期。
- **接口就绪（条件项）**：优先通过接口串联和环境变量解决数据；唯一运行时数据默认无需清理。无关键冲突且数据可串联获得时标记 `api-automation-ready`；仅真实存在契约冲突、不可造特殊分支或不可控共享配置时标记 `api-automation-blocked`。

## 可复制提示词

下次需要字段级接口用例时，可直接复制：

```text
请启用接口契约模式，根据需求文档和 Apifox 接口文档生成字段级接口测试用例。

要求：
1. 通过 Apifox CLI 只读获取 endpoint 及关联 schema，并递归解析 $ref；
2. 明确每个请求字段的具体取值、类型、数据来源和选择原因；
3. 对所有响应字段写明 JSONPath、期望值/引用值/计算关系，或不校验的原因；
4. 区分需求事实、接口契约、合理假设、待确认项和来源冲突；
5. 业务预期以需求及已确认规则为准，接口结构以 Apifox 契约为准，不用实际响应反向生成预期；
6. 只生成测试用例，不生成 Apifox/pytest 自动化脚本；
7. 优先用前序接口串联实时造数并传递变量；唯一运行时订单/会籍默认无需清理，不得仅因缺少清理接口标记 blocked；
8. 信息完整且数据可通过接口串联、环境变量或受控Setup获得的接口用例标记 api-automation-ready，否则标记 api-automation-blocked 并列出真实阻塞项；
9. 保持现有 tc-p1/tc-p2/tc-p3、pc/步骤→单一预期/rc/tag 的 Markdown 与 XMind 兼容格式。
```
