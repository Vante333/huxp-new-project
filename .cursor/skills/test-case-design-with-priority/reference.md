# 功能测试用例设计规范（含优先级体系）

本文档提供完整的功能测试用例编写规范，包括从需求分析到用例设计的全流程指导，确保格式统一、优先级清晰、内容可验证，并兼容XMind等工具导入。

---

## 一、需求分析与测试点提取方法

### 1.1 先建立需求事实基线

设计测试点前，先识别输入材料及其权威性：

1. 需求正文与已确认验收标准。
2. 产品原型、接口契约、字段字典和业务规则表。
3. 已确认的澄清记录与变更记录。
4. 现网行为、历史用例和历史缺陷，仅用于兼容性参考，不得反向覆盖新需求。

如来源冲突，记录“冲突项、来源、影响范围、建议解释”，不要自行选择后伪装成确定事实。先界定本次**新增、修改、不变、明确不测、依赖项**，避免无边界发散。

#### 1.1.1 通用功能模式与接口契约模式

本规范默认使用**通用功能模式**。页面、流程、配置、权限、消息、任务等非接口用例不要求 Method、Path、endpointId、请求 Body 或 Apifox 文档。

用户明确提出“接口契约模式”，或明确要求结合 API/Apifox 契约生成接口用例时，才叠加**接口契约模式**：

1. 需求文档及已确认澄清定义业务条件、处理规则、业务结果和副作用。
2. Apifox/OpenAPI 定义 Method、Path、请求/响应字段结构、类型、必填、格式、枚举、长度和 null 约束。
3. 接口示例、历史用例和当前环境响应仅作参考，不得反向覆盖业务预期。
4. 同一需求同时包含 UI 与 API 时按用例分别判定模式；非接口用例不得因为缺少 endpointId 或 Body 被标记阻塞。

使用 Apifox CLI 获取契约时，先 `endpoint list/get` 唯一定位接口，再对接口中的 `$ref` 递归执行 `schema get`。只读取顶层 endpoint、未展开请求或响应模型时，不得声称字段契约完整。接口名称只能用于缩小候选范围，最终须以 **Method + 标准化 Path** 消除歧义。

来源发生冲突时记录：字段路径、需求结论、契约结论、影响用例、待确认问题。不得为了让后续自动化“可生成”而任选一个值；未解决的关键冲突应使对应接口用例标记为 `api-automation-blocked`。

### 1.2 需求原子化

将复合语句拆为最小可验证单元，每个需求点分配唯一 ID：

> 本节表格仅用于Agent内部分析与覆盖反查，不得作为`需求原子化`章节写入`testcases/**/*.md`。

```markdown
| 需求ID | 角色/对象 | 触发条件 | 操作/处理 | 可观察结果 | 约束/来源 | 状态 |
| --- | --- | --- | --- | --- | --- | --- |
| R-001 | 已登录会员 | 订单可预订 | 提交预订 | 创建订单并返回订单号 | 需求§3.2 | 已确认 |
| R-002 | 同一会员 | 相同幂等键重复提交 | 系统去重 | 不重复创建订单 | 根据接口幂等约定推断 | 假设待确认 |
```

原子化时逐项扫描：

- **功能与流程**：入口、前置、主流程、分支、退出、失败恢复。
- **业务规则**：条件、动作、互斥、优先级、默认行为、组合关系。
- **字段与数据**：类型、必填性、格式、范围、精度、默认值、枚举、字段联动、增删改查。
- **状态**：初态、合法迁移、禁止迁移、终态、重复迁移、回退。
- **角色与权限**：功能权限、数据权限、租户隔离、越权访问。
- **时间**：时区、生效/失效、跨日、超时、顺序、延迟任务。
- **一致性与副作用**：落库、缓存、消息、账务/权益、审计日志、失败回滚。
- **兼容性与非功能**：历史数据、旧客户端、容量、性能、安全、可观测性。

### 1.3 隐含需求挖掘

隐含需求不是随意扩写。应从明确事实、系统契约或高概率风险推导，并标注依据：

| 观察角度 | 必问问题 | 典型测试点 |
| --- | --- | --- |
| 用户目标 | 用户真正想完成什么？失败后如何继续？ | 中断恢复、重复操作、反馈可理解 |
| 上下游契约 | 依赖失败、超时、返回脏数据会怎样？ | 超时、重试、降级、数据不一致 |
| 数据资产 | 失败是否造成资金/权益/库存多扣少扣？ | 原子性、回滚、对账、重复消费 |
| 幂等与并发 | 双击、重放、并发修改是否安全？ | 去重、锁冲突、版本控制 |
| 权限与隔离 | 能否横向/纵向越权？ | 角色切换、跨用户、跨租户 |
| 生命周期 | 过期、撤销、终态后还能操作吗？ | 非法迁移、重复迁移、过期边界 |
| 历史兼容 | 旧数据缺字段或使用旧规则怎么办？ | 缺省值、迁移、版本兼容 |
| 审计与可观测 | 关键操作能否追责和排障？ | 操作日志、关联 ID、敏感信息脱敏 |

对每个推导项使用以下状态之一：

- **已确认**：需求或已确认材料直接支持。
- **合理假设**：有明确依据，但尚未得到需求方确认；写明依据和错误时的影响。
- **待确认**：存在两种以上合理解释，且会改变预期结果。
- **不在范围**：有意排除，并说明排除依据。

不得虚构错误码、阈值、字段值或系统行为。关键歧义涉及资金/权益、权限、核心状态或数据结果时，应提出聚焦问题；未确认前可以设计分支用例，但预期必须标注“待需求确认”。

### 1.4 从用户视角构建场景

按“用户是谁—为何操作—如何操作—看到什么—失败后怎么办”检查：

- 新用户、存量用户、不同角色、不同租户或配置。
- 首次、重复、高频、连续、跨端操作。
- 误输入、误点击、取消、返回、刷新、重复提交。
- 网络中断、超时、页面关闭、重启后继续、失败重试。
- 提示是否及时、准确、可理解，是否给出可执行的恢复路径。
- 用户看到的结果是否与数据落库、账务/权益、消息和下游结果一致。

### 1.5 测试点提取模板

以下模板是内部设计草稿，不是测试用例文件模板。完成映射后只将模块和`tc-p*`用例落盘，不输出`需求事实与范围`、`测试模型`或`追溯关系`章节。

```markdown
## [功能模块名称]

### 需求事实与范围
- 已确认：
- 假设：
- 待确认：
- 不在范围：

### 测试模型
- 流程：基本流 / 备选流 / 异常流 / 恢复流
- 规则：条件与动作判定表
- 状态：合法与非法状态迁移
- 数据：有效/无效等价类与边界
- 风险：权限、并发、幂等、一致性、上下游异常

### 追溯关系
| 需求ID | 测试点ID | 测试点 | 设计方法 | 风险 | 对应用例 |
| --- | --- | --- | --- | --- | --- |

```

### 1.6 需求到用例的映射关系

| 需求类型 | 用例设计重点 | 优先级建议 |
|---------|------------|----------|
| 核心业务流程 | 主路径正向场景 | P1 |
| 关键业务规则 | 规则覆盖+边界值 | P1/P2 |
| 新增字段/功能 | 字段全场景覆盖 | P1/P2 |
| 错误码定义 | 每个错误码触发场景 | P2/P3 |
| 边界条件 | 最大/最小/空值 | P2 |
| 性能要求 | 性能测试场景 | P3 |
| 兼容性要求 | 多环境/版本测试 | P3 |

优先级最终以失败影响、发生概率、核心链路位置和可恢复性综合判定，不得仅根据使用的设计方法机械分配。

## 二、用例优先级体系

### 2.1 优先级定义

> 说明：本规范采用 **P1、P2、P3** 三个等级作为用例优先级，**不再使用 P0**。  
> 如果历史文档中仍存在 P0-P3 体系，可按以下方式迁移：**原 P0→P1，原 P1→P2，原 P2/P3→P3**。

| 优先级 | 标识 | 定义 | 执行频率 | 影响范围 |
|-------|------|------|---------|---------|
| **P1** | tc-p1 | 核心业务流程，阻塞性缺陷会导致系统不可用或核心功能完全失效 | 每次必测 | 影响所有用户，业务无法进行 |
| **P2** | tc-p2 | 重要功能点，缺陷会影响主要业务场景或关键规则 | 每次必测 | 影响大部分用户或关键业务场景 |
| **P3** | tc-p3 | 常规功能点、边缘场景、优化建议、兼容性验证 | 回归/全量测试 | 影响部分或少量用户或特定场景 |

### 2.2 优先级判定标准

#### P1级用例判定条件（满足任一即为P1）：
- ✅ 核心业务主流程（如用户登录、支付下单、权益使用）
- ✅ 数据安全相关（如权限校验、敏感信息保护）
- ✅ 资金/积分/权益的正确性（涉及用户资产）
- ✅ 系统可用性验证（服务是否正常启动/响应）
- ✅ 阻塞性缺陷场景（失败会导致后续流程无法进行）

#### P2级用例判定条件：
- ✅ 重要业务规则验证（如买点编辑规则、权益计算规则）
- ✅ 关键字段的增删改查
- ✅ 主要错误码覆盖
- ✅ 高频使用场景
- ✅ 数据一致性验证

#### P3级用例判定条件：
- ✅ 边界值、临界值测试
- ✅ 辅助功能验证
- ✅ 提示信息准确性
- ✅ 非关键错误码覆盖
- ✅ 日志记录验证
- ✅ 罕见分支场景
- ✅ 性能优化验证
- ✅ 兼容性测试
- ✅ 用户体验细节
- ✅ 非功能性需求验证

### 2.3 用例命名规范

#### 测试用例前缀格式

- **不带优先级**：`tc: 用例名称`（默认优先级，适用于无需区分优先级的场景）
- **带优先级**：`tc-p1: 用例名称` / `tc-p2: 用例名称` / `tc-p3: 用例名称`

> 说明：前缀中的 `p1`/`p2`/`p3` 对应优先级 P1/P2/P3，使用**小写**。

#### 模块命名规则

1. **接口路径转模块名**：将 API 路径中的 `/` 替换为 `_`，去掉开头的 `/`
   - `/v2/orders/{modules}/memberships/prebooking/preview` → `v2_orders_{modules}_memberships_prebooking_preview`
   - `/v2/memberships` → `v2_memberships`
   - `/v2/entitlements/search` → `v2_entitlements_search`

2. **名称不含空格**：模块名称和测试用例名称中**不能包含空格**，英文部分使用 PascalCase
   - ✅ `预览订单接口（PreviewMembershipPrebookingOrder）`
   - ❌ `预览订单接口（Preview Membership Prebooking Order）`
   - ✅ `权益查询接口（SearchEntitlements）`
   - ❌ `权益查询接口（Search Entitlements）`

3. **中文模块名简洁明了**：模块名称应简洁，括号内使用英文接口名作为标识
   - 示例：`预览订单接口（PreviewOrder）`、`权益查询接口（SearchEntitlements）`

## 三、测试用例设计方法

### 3.1 经典设计方法

#### 1. 等价类划分 (Equivalence Class Partitioning)
- **适用场景**：输入域可划分为有效/无效类别
- **操作步骤**：
  1. 识别输入变量（如：用户名、密码、数量）
  2. 划分有效等价类（符合规则的输入集合）
  3. 划分无效等价类（不符合规则的输入集合）
  4. 从每个等价类中选取代表值进行测试
- **优先级建议**：有效等价类P1/P2，无效等价类P2/P3

#### 2. 边界值分析 (Boundary Value Analysis)
- **适用场景**：有明确边界的输入（数值、长度、日期）
- **测试点**：
  - 最小值（Min）
  - 最小值+1（Min+1）
  - 正常值（Normal）
  - 最大值-1（Max-1）
  - 最大值（Max）
  - 超最小值（Min-1）
  - 超最大值（Max+1）
  - 空值（Null/Empty）
- **优先级建议**：Min、Max、Null为P2，其他为P3

#### 3. 判定表驱动法 (Decision Table Testing)
- **适用场景**：多条件组合场景（如：A条件+B条件→不同结果）
- **步骤**：
  1. 列出所有条件（条件桩）
  2. 列出所有可能的动作（动作桩）
  3. 填写判定表，标记每种组合的预期结果
  4. 简化判定表（合并相同结果的规则）
- **优先级建议**：核心业务组合P1，常见组合P2，边缘组合P3

#### 4. 场景法 (Use Case/Scenario Testing)
- **适用场景**：模拟用户真实操作流程
- **设计要点**：
  - 基本流：正常业务路径（P1）
  - 备选流：分支路径（P2）
  - 异常流：错误处理路径（P2/P3）
- **优先级建议**：主流程P1，备选流P2，异常流P2/P3

#### 5. 错误猜测法 (Error Guessing)
- **适用场景**：基于经验推测薄弱点
- **常见错误类型**：
  - 空值/Null处理
  - 特殊字符（SQL注入、XSS）
  - 并发冲突
  - 网络异常/超时
  - 权限绕过
- **优先级建议**：安全相关P1，其他P2/P3

#### 6. 状态迁移法 (State Transition Testing)
- **适用场景**：系统有明确状态流转
- **测试点**：
  - 正常状态转换（P1）
  - 非法状态转换（P2）
  - 状态回退（P3）
  - 状态并发（P3）
- **优先级建议**：主状态流转P1，异常状态P2/P3

#### 7. 流程分析法 (Flow Analysis)
- **适用场景**：跨页面、跨接口、跨系统的连续业务链路
- **操作步骤**：
  1. 标出开始、结束、处理节点、判断节点和外部依赖。
  2. 提取基本流、每条备选流、异常流和失败恢复流。
  3. 验证分支汇合点、数据传递、补偿/回滚及最终一致性。
  4. 对核心链路采用端到端场景，对单节点规则另用等价类或判定表细化。
- **优先级建议**：核心端到端基本流 P1；高频备选流和可恢复异常 P2；低概率非关键分支 P3。

#### 8. 正交/成对组合覆盖 (Orthogonal/Pairwise Testing)
- **适用场景**：角色、配置、环境、数据类型等多因子组合，穷举成本过高
- **操作步骤**：
  1. 列出因子及水平，先剔除业务上不可能或无意义的组合。
  2. 标记必须单独覆盖的高风险组合，不交给算法缩减。
  3. 对剩余组合采用成对或正交覆盖，确保任意两个因子水平至少组合一次。
  4. 补充历史缺陷、边界值和核心业务组合。
- **限制**：不可用正交法替代明确判定表中的每条业务规则；涉及资金、权益、权限的关键组合必须按风险补齐。

### 3.2 设计方法选择指南

| 需求特征 | 推荐方法 | 示例场景 |
|---------|---------|---------|
| 输入有明确范围 | 等价类划分 + 边界值分析 | 数量字段、金额字段 |
| 多条件组合 | 判定表驱动法 | 权限控制、规则校验 |
| 用户操作流程 | 场景法 | 注册→登录→下单 |
| 状态变化 | 状态迁移法 | 订单状态、会籍状态 |
| 复杂规则 | 判定表 + 等价类 | 促销规则、计费规则 |
| 安全测试 | 错误猜测法 | 注入攻击、权限绕过 |
| 跨系统长链路 | 流程分析 + 场景法 | 预览→创建→支付→查询 |
| 多因子且组合过多 | 分类树 + 成对/正交法 | 角色×配置×终端×数据类型 |

方法选择后必须留下“为何使用该方法、覆盖了哪些类/边/组合、主动排除了什么”的简短记录。不要为了展示方法而机械套用全部方法。

### 3.3 预期结果设计

预期结果必须可观察、可比较，并覆盖必要的副作用：

- **响应/界面**：状态、字段、提示、跳转、可用操作。
- **业务结果**：计算值、业务规则命中结果、状态变化。
- **数据结果**：新增/修改/删除是否正确持久化，失败时是否保持不变。
- **上下游结果**：消息、回调、缓存、库存、账务、权益是否一致。
- **安全与审计**：越权不泄露数据，敏感信息脱敏，关键操作有审计记录。

避免“正常”“成功”“符合预期”等无法独立判定的表述。若契约尚未确认，写明具体待确认项，不得伪造确定值。

### 3.3.1 接口字段级取值与断言（接口契约模式）

接口用例应先建立字段清单，再写步骤。字段清单不要求新增 Markdown 语法，可放入 `pc:` / `rc:` 或需求分析区；但必须让后续生成器无需猜测即可得到以下信息。

#### 请求字段五要素

每个 Header、Path、Query、Body 字段必须记录：

1. **完整路径**：如 `header.X-Program-ID`、`body.profile.email`。
2. **取值**：明确字面值，或明确变量名；不得只写“有效值”“正常参数”。
3. **类型**：string、number、integer、boolean、array、object、null；`false` 与 `"false"` 不等价。
4. **来源**：需求固定值、受控测试数据、环境变量、鉴权响应、前序步骤响应或运行时生成。
5. **选择原因/约束**：如边界值、等价类、正则、长度、枚举、唯一性或业务配置。

动态字段不能伪造固定值。正确写法是“`membershipId={{Setup.membershipId}}`，来自 SETUP-S01 创建响应”，而不是复制文档示例 ID。运行时随机值须说明生成规则及是否需要在后续步骤复用。

#### 响应字段处理结论

对契约声明的全部响应字段至少给出一种处理结论，避免“只断言几个顺眼字段”：

- **固定值**：`code=0`、`status="PENDING"`。
- **请求回显**：`data.extra.appId` 与 `body.appId` 一致。
- **前置基准**：`originalAmount` 等于独立商品查询得到的 `expectedOriginalAmount`。
- **业务关系**：`amount=quantity×unitPrice`、`payableAmount=originalAmount-deductionAmount`（仅当需求确认该公式）。
- **结构/类型**：字段非空、类型正确、数组项结构符合契约。
- **本用例不校验**：写明不属于本用例目的、值动态且无独立预言机，或需求/契约冲突待确认。

“本用例不校验”不是遗漏许可：核心业务字段不得无理由跳过；冲突影响核心结论时应标记 `api-automation-blocked`。禁止从同一被测响应取值作为自身期望，例如把实际 `payableAmount` 保存为 expected 后再与实际比较。

#### 字段级拆步

仍遵循“一步一果”。一次请求可先断言 HTTP/业务处理结果，再按关键 JSONPath 拆分字段步骤。多个紧密相关且失败定位一致的字段可合并为一个预期句；金额、状态、ID 流转、权益/库存副作用等核心结果应独立成步。

接口用例还必须明确：

- 前置造数及其成功判定；优先由同一用例或会话内的前序接口实时创建数据，而不是依赖长期手工ID；
- 步骤间变量生产者与消费者；
- 写操作产生的订单、会籍、权益等副作用；
- 是否需要隔离、恢复或清理，以及判断依据；
- 正向业务失败不得“可跳过”，环境依赖不足的 Skip 也不得计为 Pass。

#### 接口串联造数与清理判定

接口契约模式下，测试数据优先级如下：

1. **前序接口串联（首选）**：例如 `Preview → Create → Payments → Details`，取消/退款场景可继续调用已确认的取消接口并再次查询。每一步保存明确的响应变量，如 `Create.data.orderId`，供后续步骤消费。
2. **环境变量/受控配置**：商品A/B、Program、优惠券、模板Program、独立价格基准等稳定数据通过环境变量或数据集提供；根据本次选择的商品引用对应变量断言。
3. **专用Setup接口或运行时生成**：仅当前序业务接口无法创建目标状态时使用。
4. **手工固定ID（最后选择）**：须说明有效期、环境归属和失效处理，不得作为主链路默认方案。

使用唯一 email、clientUserId、订单号等隔离每次执行时，运行产生的订单、支付动作、会籍等业务记录**默认无需删除**。以下情况才要求恢复、隔离或清理：

- 修改共享商品、价格、Program、券或模板配置；
- 使用真实资金、真实权益或不可逆外部动作；
- 消耗数量有限、不可重复生成的测试资源；
- 残留数据会改变同次或后续用例的判断结果；
- 合规、安全或环境治理明确要求清理。

因此，缺少删除订单/会籍的接口本身不构成 `api-automation-blocked`。如果目标数据可通过接口串联得到，且唯一数据能够避免相互污染，应标记为 `api-automation-ready`。只有无法造出特殊状态（如支付失败、发放失败）、无法受控修改共享配置、缺少必要外部依赖或核心预期未确认时，才视为真实阻塞。

### 3.4 用例精简与合并原则

> **核心理念**：用最少的用例实现最全的场景覆盖。优先合并同构场景，消除跨章节重复，避免机械式穷举。

#### 合并条件 — 满足以下任一即应合并为一条用例：

1. **同构场景合并**：多个场景仅某个变量不同，验证逻辑完全一致时，合并为**一条用例 + 参数化数据表**
   - 典型信号：用例之间仅数值/类型不同，预期结果的结构一样
   - 示例：持卡人权益 4 种迁移场景（无限→有限、无限→无限、有限→无限、有限→有限）→ 合并为一条用例 + 4 行数据表

2. **对称角色合并**：多个角色/类型遵循完全相同的规则时，在同一条用例中列出适用角色，不逐一拆分
   - 典型信号：用例 B 的预期结果写了"逻辑与 A 一致"
   - 示例：持卡人权益和携伴权益遵循相同迁移逻辑 → 合并为一条，参数表中标注"持卡人/携伴"

3. **组合矩阵覆盖**：多变量组合且逻辑统一时，使用判定表/决策矩阵一次性覆盖，不逐一枚举
   - 典型信号：2-3 个变量的笛卡尔积产生 4-8 种组合，每种组合的验证模式一致
   - 示例：`权益类型(共享/买点) × 目标有无明细(有/无)` = 4 种组合 → 一条用例 + 4 行矩阵

#### 去重规则：

1. **错误码去重**：每个错误码只在首次触发的业务场景中验证，不再单独设章节重复。如果所有错误码都已被业务场景覆盖，则不设"错误码汇总"章节
2. **回归去重**：如果某场景已在正向流程中覆盖，回归章节不再重复，仅补充与正向流程有差异的验证点
3. **边界内聚**：同一字段/规则的多个边界值合并为一条参数化用例，不逐个拆分

#### 拆分条件 — 满足以下任一才应拆分为独立用例：

1. **逻辑差异**：验证逻辑存在本质差异（非仅数据值不同），预期结果的判断方式不同
2. **前置隔离**：前置条件截然不同，无法共享同一测试上下文
3. **独立定位**：核心主流程的关键步骤需要失败时能独立定位问题
4. **优先级差异**：合并后无法准确标注优先级（如 P1 场景不应与 P3 边界值混在同一条用例中）

#### 精简效果自检：

在完成用例设计后，逐条检查以下问题：
- [ ] 是否存在两条用例仅数据值不同、验证逻辑完全一致？→ 应合并
- [ ] 是否存在用例 B 写了"逻辑与 A 一致"？→ 应合并到 A
- [ ] 是否存在错误码在多个章节被重复验证？→ 保留首次出现，删除重复
- [ ] 是否存在回归用例与正向用例验证点完全相同？→ 删除回归用例或仅保留差异点

## 四、用例文档结构规范

### 4.1 核心结构（脑图导入格式）

> 本结构兼容 XMind 等脑图工具导入，根节点不导入系统，模块支持最多 8 层嵌套。
>
> `testcases/**/*.md`默认采用纯用例结构：只允许H1、业务/接口模块和`tc-p*`用例。不得混入`测试范围说明`、`需求原子化`、`需求事实与范围`、`测试模型`、`契约冲突与自动化阻塞项`、`共性测试数据`、`覆盖追溯`或`执行与自动化门禁`等全局分析章节。相关信息应写入具体用例的`pc/rc`；确需保留分析时另建文档。

```markdown
# [文档主标题]（根节点，不导入系统）

## [功能模块1]

### [子模块]

#### tc-p1: [测试用例名称]

- pc: [前置条件]
- [步骤1]
  - [预期结果1]
- [步骤2]
  - [预期结果2]
- rc: [备注]
- tag: [标签1],[标签2]
```

**格式要点**：
- **根节点**（H1）：文档主标题，导入脑图后作为根节点，**不导入测试管理系统**
- **模块层级**（H2 及以下）：功能模块，支持最多 8 层嵌套
- **测试用例**：使用 `tc:` 或 `tc-p{n}:` 前缀标识，位于模块层级下方
- **用例子节点**（列表项）：
  - `pc:` — 前置条件（非必填）
  - 步骤 → 预期结果（步骤为一级列表项，预期结果为其子列表项）
  - `rc:` — 备注（非必填）
  - `tag:` — 标签，多个用逗号分隔（非必填）
- **模块和用例名称不能包含空格**，英文部分使用 PascalCase
- **接口路径作为模块名时**，用 `_` 替代 `/`

### 4.1.1 自动化就绪接口用例模板

接口契约模式继续使用既有 `pc:`、步骤→单一预期、`rc:`、`tag:`，不新增破坏 XMind 导入的前缀：

```markdown
##### tc-p1: [业务条件下的明确预期]

- rc: 覆盖R-001；接口POST /v2/example；endpointId=[可选追踪值]
- pc: header.X-Program-ID={{ProgramID}}；类型=string；来源=测试数据集
- pc: body.amount=50.50；类型=number；来源=受控商品基准；原因=验证正常算价
- pc: body.profile.email="preview@example.com"；类型=string；来源=本用例固定值；约束=满足接口正则
- S01：按上述字段调用POST /v2/example
  - HTTP状态码=200且业务码code=0
- S02：检查data.extra.profile.email
  - data.extra.profile.email与body.profile.email完全一致
- S03：检查data.payment.price.originalAmount
  - data.payment.price.originalAmount=50.50，等于独立前置数据expectedOriginalAmount
- S04：检查data.payment.price.payableAmount
  - data.payment.price.payableAmount=50.50，符合已确认的原价购买规则
- rc: data.payment.paymentStatus存在需求与契约冲突，本用例不生成该字段断言；若影响本用例核心目的则改标blocked
- tag: api,api-automation-ready
```

标签判定：

- `api-automation-ready`：接口唯一，`$ref` 已解析，请求字段均有值和来源，关键响应预期均有独立依据，变量可通过前序接口、环境变量或受控Setup获得；唯一运行时业务数据无需清理。
- `api-automation-blocked`：存在接口歧义、关键 `$ref` 未解析、必填入参无来源、核心业务预期冲突、错误码未确认、特殊状态无法造出，或共享配置/真实资金权益无法安全隔离。不得仅因缺少删除订单/会籍接口标记 blocked；必须用 `rc:` 逐项列出真实阻塞字段和原因。

非接口用例不使用上述 API 门禁，继续按 4.1 的通用格式生成。

### 4.2 层级详细说明

#### 根节点（H1） — 文档主标题
- **标记**：`#`
- **用途**：脑图根节点，**不导入测试管理系统**
- **格式**：`# {需求名称}测试用例`
- **示例**：`# 会籍权益系统API测试用例`

#### 模块层级（H2 及以下） — 功能模块
- **标记**：`##`、`###`、`####` 等，最多支持 8 层嵌套
- **用途**：按功能、接口、场景分类组织测试用例
- **格式**：`## {模块名称}`
- **命名规则**：
  - 接口路径中的 `/` 替换为 `_`：`/v2/entitlements/search` → `v2_entitlements_search`
  - 名称不含空格，英文使用 PascalCase：`权益查询接口（SearchEntitlements）`
- **示例**：
  - `## 权益查询接口（SearchEntitlements）`
  - `### 买点字段返回规则`
  - `#### 正向场景验证`

#### 测试用例节点 — `tc:` 或 `tc-p{n}:` 前缀

测试用例位于模块层级下方，使用**标题**标识，前缀规则如下：

| 前缀 | 含义 | 示例 |
|------|------|------|
| `tc:` | 不带优先级的测试用例 | `##### tc: 用户首次查询权益不返回purchasedEntitlements字段` |
| `tc-p1:` | P1 优先级测试用例 | `##### tc-p1: 用户已充值查询权益返回purchasedEntitlements字段` |
| `tc-p2:` | P2 优先级测试用例 | `##### tc-p2: 用户未充值查询权益不返回purchasedEntitlements字段` |
| `tc-p3:` | P3 优先级测试用例 | `##### tc-p3: 用户充值点数为0验证purchasedEntitlements字段返回` |

**要求**：
- 用例名称**不能包含空格**，英文部分使用 PascalCase
- 场景描述应清晰、完整、可执行，包含关键测试数据和条件

#### 用例子节点（列表项） — pc / 步骤→预期结果 / rc / tag

测试用例标题下方使用**列表项**描述用例详情，包含以下元素：

| 前缀 | 含义 | 必填性 | 格式说明 |
|------|------|--------|---------|
| `pc:` | 前置条件 | 非必填 | `- pc: 用户已登录且账户状态正常` |
| （无前缀） | 测试步骤 | 必填 | `- 调用GET_v2_entitlements_search接口` |
| （缩进子项） | 预期结果 | 必填 | `  - HTTP状态码为200` |
| `rc:` | 备注 | 非必填 | `- rc: 需要先配置充值模板` |
| `tag:` | 标签 | 非必填 | `- tag: 权益,买点,P1`（多个用逗号分隔） |

**步骤与预期结果的对应关系**：
- 步骤为**一级列表项**（`-`）
- 预期结果为步骤的**子列表项**（缩进 `  -`）
- **每个步骤最多有一个预期结果**，不能有多个预期结果
- 如果一个操作需要验证多个结果，应拆分为多个步骤

```markdown
##### tc-p1: 用户已充值查询权益返回purchasedEntitlements字段

- pc: 用户已完成充值，账户中存在买点余额
- 调用GET_v2_entitlements_search接口查询用户权益
  - HTTP状态码为200，响应中包含purchasedEntitlements字段，值等于用户实际充值的点数，maxGuestsNextUse的计算包含了purchasedEntitlements
- rc: 需确认充值模板已配置
- tag: 权益查询,买点,正向验证
```

**编写建议**：
- 步骤描述应清晰表达操作动作（如"调用XX接口"、"传入XX参数"）
- 预期结果应包含具体的验证点（如字段名、值、状态码），而非笼统描述
- **每个步骤只能有一个预期结果**，多个验证点应合并为一句话或拆分为多个步骤
- 前置条件应融入 `pc:` 节点，不单独设置段落

#### 参数化用例格式（合并同构场景时使用）

当多个场景符合 3.4 节合并条件时，使用**参数化数据表 + 统一步骤和预期结果**的格式：

```markdown
##### tc-p1: 持卡人/携伴权益按「原余额类型×目标模板类型」四种场景迁移

| 原权益 | 目标模板 | 迁移后目标余额 | 适用角色 |
|--------|---------|--------------|---------|
| 无限(-1) | 有限(N) | 0 | 持卡人/携伴 |
| 无限(-1) | 无限(-1) | -1 | 持卡人/携伴 |
| 有限(M) | 无限(-1) | -1 | 持卡人/携伴 |
| 有限(M) | 有限(N) | M（按原余额迁移） | 持卡人/携伴 |

- 按上表数据组合执行权益迁移
  - 每种组合下持卡人和携伴均遵循相同迁移逻辑，迁移结果符合上表预期
```

**参数化格式规则**：
- 数据表放在用例标题之后、步骤和预期结果之前
- 表头应清晰标注变量名和预期结果列
- 预期结果中使用"符合上表预期"进行引用，避免逐行重复
- 当表格行数 ≤ 8 行时使用参数化合并；超过 8 行应考虑按逻辑分组拆分

### 4.3 完整示例

```markdown
# 会籍权益系统买点功能测试用例

## 权益查询接口（SearchEntitlements）

### 买点字段返回规则

#### 正向场景验证

##### tc-p1: 用户已充值查询权益返回purchasedEntitlements字段

- pc: 用户已完成充值，账户中存在买点余额
- 调用GET_v2_entitlements_search接口查询用户权益
  - HTTP状态码为200，响应中包含purchasedEntitlements字段，值等于用户实际充值的点数，maxGuestsNextUse的计算包含了purchasedEntitlements

##### tc-p2: 用户未充值过查询权益不返回purchasedEntitlements字段

- pc: 用户从未进行过充值操作
- 调用GET_v2_entitlements_search接口查询用户权益
  - HTTP状态码为200，响应中不包含purchasedEntitlements字段，其他权益字段正常返回，maxGuestsNextUse仅基于非买点的共享点计算

#### 边界值验证

##### tc-p3: 用户充值点数为0验证purchasedEntitlements字段返回

- pc: 用户充值点数为0
- 调用GET_v2_entitlements_search接口查询用户权益
  - 返回purchasedEntitlements字段，值为0，不影响其他权益字段

## 权益编辑接口（UpdateEntitlements）

### 买点编辑规则

#### 充值模板校验

##### tc-p1: 未配置充值模板时编辑买点返回错误码500.030.024

- pc: 当前项目未配置充值模板
- 调用PUT_v2_entitlements接口编辑买点
  - 返回错误码500.030.024，错误信息为OperationNotAllowed.EditingThisTypeOfEntitlementIsNotSupportedBasedOnTheProgramSettings.，买点数量未发生变化

#### 同时更新限制

##### tc-p1: 同时更新买点和权益点返回错误码500.030.025

- pc: 用户存在买点和权益点
- 调用PUT_v2_entitlements接口同时更新买点和权益点
  - 返回错误码500.030.025，错误信息为OperationNotAllowed.DifferentTypesOfEntitlementsMustBeUpdatedSeparately.，买点和权益点数量均未变化

#### 边界值验证

##### tc-p2: 将买点增加到999（上限值）更新成功

- pc: 用户当前买点余额充足
- 调用PUT_v2_entitlements接口将买点设置为999
  - 更新成功，买点值为999
- 再次查询确认数据持久化
  - 买点值仍为999

##### tc-p2: 将买点增加到1000（超上限）返回错误

- pc: 用户当前买点余额充足
- 调用PUT_v2_entitlements接口将买点设置为1000
  - 更新失败，返回错误提示（超出限制），买点值未变化

##### tc-p2: 买点减少到0更新成功

- pc: 用户当前存在买点余额
- 调用PUT_v2_entitlements接口将买点减少到0
  - 更新成功，买点值为0，purchasedEntitlements字段仍然返回且值为0

##### tc-p1: 买点减少到负数返回错误码500.030.012

- pc: 用户当前存在买点余额
- 调用PUT_v2_entitlements接口将买点减少到负数
  - 更新失败，返回错误码500.030.012，错误信息为InsufficientEntitlementBalance.TheRequestedDeductionExceedsTheAvailableEntitlement.，买点值未变化
- rc: 需验证扣减金额大于当前余额的场景

#### 计算规则验证

##### tc-p1: 更新买点后maxGuestsNextUse计算正确（sharedEntitlements=3,purchasedQuantity=5）

- pc: 用户sharedEntitlements=3，allowedGuestsPerUsage=1
- 调用PUT_v2_entitlements接口将purchasedEntitlements更新为5
  - purchasedEntitlements更新为5，maxGuestsNextUse=(3+5)/1=8，买点作为共享点参与计算
```

#### 精简性检查
- [ ] 无同构场景被拆分为多条独立用例（应合并为参数化用例）

- [ ] 无回归用例与正向用例验证点完全相同（应删除或仅保留差异点）
- [ ] 总用例数在合理范围内（见下方参考）

### 6.2 优先级分布与用例数量参考

合理的优先级分布（仅供参考）：
- **P1**: 20-30%（核心业务流程，阻塞性场景）
- **P2**: 40-50%（重要规则、关键字段、主要错误码）
- **P3**: 20-30%（边界值、边缘场景、兼容性验证）

比例仅用于发现异常，不是配额。优先级应根据业务影响、发生概率、核心链路位置、数据/资产风险和可恢复性判定；不得为了满足比例强行升降级。

**总用例数参考**（精简合并后）：
- 单接口/小需求：10-20 条
- 中型需求（3-5 个模块）：25-40 条
- 大型需求（5+ 个模块）：40-60 条
- 超过 60 条应审视是否有合并空间

**警告信号**：
- ⚠️ P1 超过 40%：优先级判定过于宽松，应下调部分用例到 P2
- ⚠️ P1 低于 15%：可能遗漏核心场景
- ⚠️ 存在大量仅数据值不同的独立用例：应使用参数化合并
- ⚠️ 存在独立的"错误码汇总"章节且所有错误码已被业务场景覆盖：应删除该章节

## 八、XMind/脑图导入兼容性说明

### 8.1 导入格式要求
- 根节点（H1）：文档主标题，**不导入测试管理系统**
- 模块层级（H2 及以下）：按功能分类，支持最多 8 层嵌套
- 测试用例：使用 `tc:` 或 `tc-p{n}:` 前缀
- 用例子节点：使用列表项（`pc:`、步骤→预期结果、`rc:`、`tag:`）
- 每级标题独占一行，使用标准 Markdown 语法（#号+空格+标题）
- **模块和用例名称不含空格**，英文使用 PascalCase
- **接口路径中的 `/` 替换为 `_`**

### 8.2 导入后脑图结构
```
根节点（H1，不导入系统）
├─ 功能模块1（H2，模块支持8层嵌套）
│  ├─ 子模块1.1（H3）
│  │  ├─ 验证分类1.1.1（H4）
│  │  │  ├─ tc-p1: 测试用例名称（H5）
│  │  │  │  ├─ pc: 前置条件（非必填）
│  │  │  │  ├─ 步骤1
│  │  │  │  │  └─ 预期结果1（每个步骤最多一个预期结果）
│  │  │  │  ├─ 步骤2
│  │  │  │  │  └─ 预期结果2
│  │  │  │  ├─ rc: 备注（非必填）
│  │  │  │  └─ tag: 标签1,标签2（非必填）
```

### 8.3 注意事项
- 根节点仅作为脑图组织根，不导入测试管理系统
- 模块节点为纯组织层级，导入后作为文件夹/分类
- `tc:` / `tc-p{n}:` 前缀的节点会被识别为测试用例
- `pc:` / `rc:` / `tag:` 前缀的列表项会被识别为用例的子属性
- 步骤为一级列表节点，预期结果为步骤的子节点
- **每个步骤最多有一个预期结果**，多个验证点应合并为一句话
- 优先级标记（p1/p2/p3）便于在脑图中按颜色/标签筛选

### 8.4 XMind 导出 → testcases Markdown（仓库脚本）

**方向**：XMind（评审脑图）→ 覆盖 `testcases/**/*.md`。**不要**在对话中临时写 Python/JS 转换器。

| 场景 | 脚本 | 说明 |
| --- | --- | --- |
| 团队 `tc-p*` 用例/测试分析（默认） | `tools/xmind_to_testcases_md.py` | 输出 `### tc-p1:` + `pc`/步骤/预期；与本文 §4.1 一致 |
| 另一套 tc 汇总格式 | `tools/xmind_to_markdown_v2.py` | `##### tc-P1` 等，见脚本说明 |
| 纯大纲、无 tc 结构 | `tools/xmind2md.py` | `#` 标题 + 列表，不解析优先级 |

**推荐命令**（Windows PowerShell）：

```powershell
python tools/xmind_to_testcases_md.py `
  --xmind "D:\path\PAPI-xxxx测试用例.xmind" `
  --out "testcases/2026Q2SP4/PAPI-xxxx-测试用例-001.md" `
  --requirement "requirements/2026Q2SP4/PAPI-xxxx.md"
```

**转换后检查**：

1. 输出只包含H1、业务/接口模块和`tc-p*`用例；删除测试范围、需求分析、冲突、公共数据、追溯及自动化门禁等全局章节。
2. 原 Markdown 中的判定表/分析表若不在脑图`tc`子树下，导出后会缺失——属预期行为；如需保留应另建分析文档，不合并进用例文件。
3. 历史 `tc-p0` 在脚本内映射为 `tc-p1`；碎片节点（是/否/不适用）不写入。

**反向**（Markdown 表格 → 列表便于导入 XMind）：`tools/md_tables_to_xmind_lists.py`。

## 九、附录

### 9.1 常见错误示例

#### ❌ 错误示例1：优先级标记缺失
```markdown
##### 用户使用有效凭据登录成功
```
**问题**：缺少 `tc:` 或 `tc-p{n}:` 前缀
**正确**：
```markdown
##### tc-p1: 用户使用有效凭据登录成功
```

#### ❌ 错误示例2：使用 H6 子标题分隔用例内容
```markdown
##### tc-p1: 用户使用有效凭据登录成功

###### 前置条件
- 用户已注册

###### 测试步骤
1. 打开登录页面
2. 输入凭据

###### 预期结果
- 登录成功
```
**问题**：使用了 H6 子标题分段，且预期结果描述过于笼统
**正确**：
```markdown
##### tc-p1: 用户使用有效凭据登录成功

- pc: 用户已注册且账户状态正常
- 打开登录页面输入有效凭据提交登录
  - HTTP响应状态码为200，返回用户Token（格式为JWT），跳转到用户首页/dashboard，Session创建成功且有效期为2小时
```

#### ❌ 错误示例3：名称包含空格
```markdown
##### tc-p1: 用户使用有效凭据登录成功（User Login Success）

## 权益查询接口（Search Entitlements）
```
**问题**：用例名称和模块名称中包含空格
**正确**：
```markdown
##### tc-p1: 用户使用有效凭据登录成功（UserLoginSuccess）

## 权益查询接口（SearchEntitlements）
```

#### ❌ 错误示例4：接口路径未替换斜杠
```markdown
## /v2/entitlements/search接口测试
```
**问题**：接口路径中的 `/` 未替换为 `_`
**正确**：
```markdown
## v2_entitlements_search接口测试
```

#### ❌ 错误示例5：场景描述不完整
```markdown
##### tc-p2: 更新买点失败
```
**问题**：未说明失败原因和条件
**正确**：
```markdown
##### tc-p2: 未配置充值模板时更新买点返回错误码500.030.024
```

#### ❌ 错误示例6：同构场景逐一枚举（冗余）
```markdown
##### tc-p1: 持卡人权益为无限（-1）目标模板为有限（3）迁移后为0

- 执行权益迁移
  - 迁移后目标权益余额为0

##### tc-p1: 携伴权益为无限（-1）目标模板为有限（5）迁移后为0

- 执行权益迁移
  - 逻辑与持卡人一致

##### tc-p1: 持卡人权益为无限（-1）目标模板为无限（-1）迁移后为-1

- 执行权益迁移
  - 迁移后目标权益余额为-1
```
**问题**：持卡人和携伴逻辑完全一致却逐一拆分；多种组合模式相同却逐一枚举
**正确**（参数化合并）：
```markdown
##### tc-p1: 持卡人/携伴权益按「原余额类型×目标模板类型」四种场景迁移

| 原权益 | 目标模板 | 迁移后目标余额 | 适用角色 |
|--------|---------|--------------|---------|
| 无限(-1) | 有限(N) | 0 | 持卡人/携伴 |
| 无限(-1) | 无限(-1) | -1 | 持卡人/携伴 |
| 有限(M) | 无限(-1) | -1 | 持卡人/携伴 |
| 有限(M) | 有限(N) | M（按原余额迁移） | 持卡人/携伴 |

- 按上表数据组合执行权益迁移
  - 每种组合下持卡人和携伴均遵循相同迁移逻辑，迁移结果符合上表预期
```

#### ❌ 错误示例7：错误码跨章节重复

```markdown
## 共享权益迁移
##### tc-p1: 原等级存在无限共享权益报错

- 执行共享权益迁移
  - 返回错误码500.030.029
  - 错误信息：AbnormalEntitlementsDetected...

... 其他章节 ...

## 错误码验证
##### tc-p1: 存在异常权益时返回500.030.029

- 触发异常权益场景
  - 错误码为500.030.029
  - 英文提示为AbnormalEntitlementsDetected...
```
**问题**：错误码 500.030.029 在"共享权益迁移"章节中已完整验证，"错误码验证"章节又重复了一次
**正确**：删除"错误码验证"章节中已被业务场景覆盖的错误码用例，仅保留未被任何场景覆盖的孤立错误码。如果所有错误码均已内嵌覆盖，则不设"错误码验证"章节。

## 十、总结

### 核心原则
1. **优先级清晰**：每个用例使用 `tc:` 或 `tc-p{n}:` 前缀标识优先级
2. **脑图兼容**：根节点不导入系统，模块支持8层嵌套，用例子节点包含 `pc:` / 步骤→预期结果 / `rc:` / `tag:`
3. **一步一果**：每个步骤最多有一个预期结果，多个验证点应合并为一句话或拆分为多个步骤
4. **标题自包含**：用例标题应包含完整场景描述（条件+预期行为）
5. **命名规范**：模块和用例名称**不含空格**（英文 PascalCase），接口路径用 `_` 替代 `/`
6. **最少覆盖最全**：同构场景合并为参数化用例，消除跨章节重复，不机械穷举（详见 3.4 节）
7. **可维护性**：文档结构清晰紧凑，易于更新和扩展，兼容 XMind/脑图导入

### 使用流程
1. **需求分析** → 提取测试分析点
2. **用例设计** → 应用设计方法，编写用例（`tc-p{n}:` 格式）
3. **精简合并** → 按 3.4 节原则合并同构场景、消除重复
4. **优先级评定** → 判定 P1/P2/P3
5. **命名检查** → 确认无空格、接口路径已用 `_` 替代 `/`
6. **用例评审** → 检查完整性、准确性、精简性
7. **执行追踪** → 记录执行结果，关联缺陷
8. **持续优化** → 根据反馈更新用例

遵循本规范，可确保测试用例的高质量、高覆盖率、低冗余、高可维护性，并兼容 XMind/脑图导入。
