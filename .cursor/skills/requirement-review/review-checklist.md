# 需求评审检查清单

本清单用于阶段三逐项评审。评审时必须逐条检查，每个检查项标注 ✅（通过）或 ❌（未通过并记录问题）。

**编号规则**：`{大类编号}.{小类编号}-{序号}`，如 `1.2-④` 表示"完整性 → 接口定义完整性 → 第4项"。

---

## 一、完整性检查

### 1.1 功能描述完整性
- [ ] ① 功能目标是否明确说明
  - 🔍 检查要点：是否有清晰的"做什么"和"为什么做"
  - ⚠️ 常见问题：只描述了操作，缺少业务目的
- [ ] ② 输入/输出是否完整定义
  - 🔍 检查要点：每个操作的输入参数和输出结果是否都有说明
  - ⚠️ 常见问题：只给了请求示例但未说明每个字段含义
- [ ] ③ 前置条件是否列出
  - 🔍 检查要点：执行该功能前需要满足什么条件
  - ⚠️ 常见问题：未说明数据/状态的前置依赖
- [ ] ④ 后置状态是否描述
  - 🔍 检查要点：执行成功/失败后系统状态如何变化
  - ⚠️ 常见问题：只描述了成功场景，遗漏失败后的状态回退
- [ ] ⑤ 是否有遗漏的功能场景（正常流 + 异常流 + 边界场景）
  - 🔍 检查要点：枚举所有可能的路径，检查是否每条路径都有定义
  - ⚠️ 常见问题：缺少异常分支和边界场景

### 1.2 接口定义完整性
- [ ] ① 接口路径是否明确
  - 🔍 检查要点：URL 路径、版本号是否清晰
- [ ] ② 请求方法（GET/POST/PUT/DELETE）是否指定
  - 🔍 检查要点：是否明确标注 HTTP 方法
- [ ] ③ 请求参数是否完整（必填/选填、类型、取值范围、默认值）
  - 🔍 检查要点：每个参数是否说明了这四个属性
  - ⚠️ 常见问题：只给了字段名，缺少类型或是否必填
- [ ] ④ 响应结构是否完整定义
  - 🔍 检查要点：成功/失败的响应格式是否都有定义
  - ⚠️ 常见问题：只给了成功的响应示例
- [ ] ⑤ 错误码是否覆盖所有异常场景
  - 🔍 检查要点：对照业务规则，每条异常分支是否都有错误码
  - ⚠️ 常见问题：部分异常场景没有对应的错误码
- [ ] ⑥ 错误码格式和消息是否规范
  - 🔍 检查要点：错误码编号是否符合项目统一格式

### 1.3 业务规则完整性
- [ ] ① 业务规则是否全部列出
  - 🔍 检查要点：功能描述中隐含的约束是否提炼为明确规则
- [ ] ② 规则的触发条件是否明确
  - 🔍 检查要点：在什么情况下这条规则生效
  - ⚠️ 常见问题：规则描述模糊，如"某些情况下"
- [ ] ③ 规则的执行结果是否清晰
  - 🔍 检查要点：触发规则后具体发生什么（成功/拒绝/降级）
- [ ] ④ 规则的优先级是否定义（当规则冲突时）
  - 🔍 检查要点：多条规则同时适用时的优先判断

### 1.4 非功能需求
- [ ] ① 是否考虑性能要求（响应时间、吞吐量）
- [ ] ② 是否考虑并发场景
- [ ] ③ 是否考虑数据量级

---

## 二、一致性检查

### 2.1 内部一致性
- [ ] ① 同一文档内的术语是否统一
  - 🔍 检查要点：同一概念是否有多种叫法
  - ⚠️ 常见问题：中英文混用导致同一字段名称不统一
- [ ] ② 同一字段在不同接口中的命名是否一致
  - 🔍 检查要点：跨接口比对相同语义的字段名
- [ ] ③ 同一字段的数据类型在不同位置是否一致
  - 🔍 检查要点：比对同一字段在不同接口中的类型定义
- [ ] ④ 业务规则在不同章节的描述是否一致
  - 🔍 检查要点：同一规则在不同模块中的措辞是否矛盾

### 2.2 跨模块一致性
- [ ] ① 模块间共享数据的定义是否一致
  - 🔍 检查要点：共享字段的含义、类型、取值范围是否对齐
- [ ] ② 模块间流程衔接是否连贯
  - 🔍 检查要点：上游模块的输出是否满足下游模块的输入要求
- [ ] ③ 模块间的业务规则是否存在冲突
  - 🔍 检查要点：不同模块对同一事物的约束是否矛盾

### 2.3 与现有系统一致性
- [ ] ① 新增字段是否与现有数据模型兼容
- [ ] ② 新增逻辑是否影响现有功能
- [ ] ③ 接口变更是否保持向后兼容

---

## 三、清晰性检查

### 3.1 描述清晰度
- [ ] ① 是否存在模糊用语（"可能"、"大概"、"应该"、"等"、"之类的"）
  - 🔍 检查要点：全文搜索模糊词汇
  - ⚠️ 常见问题：用"等"省略了重要的枚举项
- [ ] ② 是否存在多义词或歧义表达
  - 🔍 检查要点：同一句话是否能有两种以上的理解
- [ ] ③ 条件判断是否有明确的 if/else 逻辑
  - 🔍 检查要点：每个条件分支是否都有处理方式
  - ⚠️ 常见问题：只描述了"如果A则B"，缺少"否则"分支
- [ ] ④ 数值计算公式是否明确
  - 🔍 检查要点：涉及计算的逻辑是否有公式或伪代码

### 3.2 术语规范
- [ ] ① 专业术语是否有定义或解释
- [ ] ② 同一概念是否使用同一术语（避免中英混用不一致）
- [ ] ③ 缩写是否有全称说明

### 3.3 示例充分性
- [ ] ① 复杂逻辑是否附带示例说明
- [ ] ② 接口请求/响应是否有示例
- [ ] ③ 计算逻辑是否有具体数值示例

---

## 四、可测试性检查

### 4.1 可验证性
- [ ] ① 每个功能点是否能编写至少一条测试用例
  - 🔍 检查要点：是否能从需求描述中提取出测试的输入和预期输出
- [ ] ② 预期结果是否具体、可量化（非"正常显示"这类模糊描述）
  - ⚠️ 常见问题：预期结果为"正常返回"而未说明返回什么
- [ ] ③ 边界值是否明确（最大值、最小值、空值）

### 4.2 测试数据
- [ ] ① 是否提供或暗示测试数据来源
- [ ] ② 特殊场景的测试数据是否可构造
- [ ] ③ 数据之间的关联关系是否清晰

---

## 五、边界与异常检查

### 5.1 边界条件
- [ ] ① 数值型字段的上下限是否定义
  - 🔍 检查要点：数值字段是否有最大值、最小值约束
  - ⚠️ 常见问题：只给了上限没给下限，或反之
- [ ] ② 字符串字段的长度限制是否定义
- [ ] ③ 列表/数组的最大数量是否定义
- [ ] ④ 空值/null 场景是否处理
  - 🔍 检查要点：字段为空时系统行为是什么
- [ ] ⑤ 零值场景是否处理
  - 🔍 检查要点：数值为0时是否有特殊语义（如"不限制"与"无"的区别）

### 5.2 异常处理
- [ ] ① 参数校验失败时的处理是否定义
- [ ] ② 业务逻辑异常时的处理是否定义
  - 🔍 检查要点：每条业务规则违反时的处理方式
- [ ] ③ 外部依赖失败时的处理是否定义
  - 🔍 检查要点：调用第三方服务超时/失败时如何处理
- [ ] ④ 并发冲突时的处理是否定义
- [ ] ⑤ 数据不一致时的处理是否定义

### 5.3 幂等性与重试
- [ ] ① 接口是否需要幂等设计
- [ ] ② 重复请求的处理策略是否明确
- [ ] ③ 超时重试的影响是否考虑

---

## 六、接口规范检查

### 6.1 RESTful 规范
- [ ] ① URL 路径命名是否符合 RESTful 风格
- [ ] ② HTTP 方法使用是否恰当
- [ ] ③ 状态码使用是否规范

### 6.2 字段规范
- [ ] ① 新增字段命名是否符合项目命名规范（驼峰/下划线）
- [ ] ② 字段类型是否合理（string/int/boolean/array/object）
- [ ] ③ 必填/选填标识是否清晰
- [ ] ④ 字段默认值是否合理
- [ ] ⑤ 枚举值是否列举完整

### 6.3 版本兼容
- [ ] ① 接口变更是否向后兼容
- [ ] ② 新增字段是否为选填（避免破坏现有调用方）
- [ ] ③ 废弃字段是否有迁移方案

---

## 七、安全性检查

### 7.1 数据安全
- [ ] ① 敏感数据是否有脱敏要求
- [ ] ② 数据传输是否需要加密
- [ ] ③ 数据存储是否需要加密

### 7.2 权限控制
- [ ] ① 接口访问是否需要鉴权
- [ ] ② 操作权限是否有明确的角色限制
- [ ] ③ 数据权限是否有隔离要求

### 7.3 输入校验
- [ ] ① 是否防范注入攻击（SQL注入、XSS等）
- [ ] ② 是否有请求频率限制
- [ ] ③ 上传文件是否有类型/大小限制
