# 需求文档评审技能

## 概述

对需求文档执行系统化评审，流程分为三个阶段：**拆分 → 关系分析 → 逐项评审**。

评审结果输出到 `review-reports/` 目录，包含模块拆分、关系图谱和逐项评审报告。

## 评审流程

### 阶段一：需求拆分

**目标**：将需求文档解析为结构化的功能模块清单。

**操作步骤**：

1. 读取用户指定的需求文档
2. 按以下维度识别功能模块：
   - 文档标题层级（H2/H3 通常对应功能模块）
   - 接口/API 端点划分
   - 业务流程边界
   - 独立的功能单元
3. 为每个模块提取：
   - **模块编号**：M1, M2, M3...
   - **模块名称**：简短描述
   - **涉及接口**：相关 API 端点列表
   - **核心功能点**：该模块要实现的关键功能
   - **业务规则**：约束条件和业务逻辑
   - **错误码**：涉及的错误码及含义
4. 将拆分结果保存到 `review-reports/{需求编号}-01-模块拆分.md`

**拆分输出格式**：

```markdown
# {需求名称} - 模块拆分

## 拆分概览

| 模块编号 | 模块名称 | 涉及接口 | 功能点数 |
|---------|---------|---------|---------|
| M1 | xxx | /v2/xxx | N |
| M2 | xxx | /v2/xxx | N |

## M1: {模块名称}

### 涉及接口
- {接口路径及方法}

### 核心功能点
1. {功能点描述}
2. ...

### 业务规则
1. {规则描述}
2. ...

### 错误码
| 错误码 | 触发条件 | 错误信息 |
|-------|---------|---------|
| xxx | xxx | xxx |

## M2: {模块名称}
...
```

### 阶段二：模块关系分析

**目标**：分析各功能模块之间的依赖和影响关系。

**操作步骤**：

1. 基于阶段一的拆分结果，逐对分析模块间关系
2. 识别以下关系类型：
   - **数据依赖**：模块 A 的输出是模块 B 的输入
   - **流程依赖**：模块 A 必须先于模块 B 执行
   - **共享实体**：多个模块操作同一数据实体
   - **规则冲突**：模块间存在潜在矛盾的业务规则
   - **影响传播**：模块 A 的变更可能影响模块 B
3. 生成关系矩阵和依赖图
4. 标记高风险关联点（强耦合、规则冲突等）
5. 将分析结果保存到 `review-reports/{需求编号}-02-关系分析.md`

**关系分析输出格式**：

```markdown
# {需求名称} - 模块关系分析

## 关系矩阵

| 源模块 | 目标模块 | 关系类型 | 关系说明 | 风险等级 |
|-------|---------|---------|---------|---------|
| M1 | M2 | 数据依赖 | xxx | 低/中/高 |

## 依赖关系图（Mermaid）

（使用 mermaid graph 展示模块依赖）

## 高风险关联点

### 风险点 1: {描述}
- **涉及模块**：M1, M3
- **风险说明**：xxx
- **建议**：xxx

## 共享实体分析

| 实体名称 | 涉及模块 | 操作类型 |
|---------|---------|---------|
| xxx | M1(读), M2(写) | CRUD |
```

### 阶段三：逐项评审

**目标**：基于评审检查清单，穷举式发现需求文档中所有问题、错误和漏洞，并给出具体的修改建议。

**核心原则**：

- **穷举式审查**：必须逐条对照 [review-checklist.md](review-checklist.md) 中的每一项检查点，不可跳过任何检查项
- **问题溯源**：每个发现的问题必须关联到具体的检查清单条目编号（如 1.2-④ 表示"一、完整性检查 → 1.2 接口定义完整性 → 第4项"）
- **原文引用**：问题描述中必须引用需求文档的原始文本，用 `>` 引用块标记
- **修改建议可落地**：每个问题的修改建议必须具体到可以直接用于修改需求文档，包含建议的补充文本或修改后的表述

**操作步骤**：

1. 读取 [review-checklist.md](review-checklist.md) 获取完整检查清单
2. 按模块编号顺序逐个评审，每个模块按 7 个维度逐项检查：
   - **完整性**：功能描述是否齐全，有无遗漏场景
   - **一致性**：模块内部及模块间是否存在矛盾
   - **清晰性**：描述是否无歧义，术语是否统一
   - **可测试性**：是否能据此编写测试用例
   - **边界与异常**：边界条件和异常处理是否完备
   - **接口规范**：接口定义是否完整准确
   - **安全性**：是否有潜在安全风险
3. 对每个问题评定严重等级：
   - 🔴 **严重**：阻塞开发或可能导致重大缺陷
   - 🟡 **一般**：需要澄清或补充，但不阻塞
   - 🟢 **建议**：优化建议，可选采纳
4. 对每个问题给出**修改建议**，建议必须包含：
   - **建议类型**：补充（新增内容）/ 修正（修改现有内容）/ 删除（移除矛盾内容）
   - **建议内容**：给出可直接采纳的具体文本或修改方案
   - **修改位置**：指出应在需求文档的哪个位置进行修改
5. 给出每个模块的评审结论和整体评审总结
6. 将评审结果保存到 `review-reports/{需求编号}-03-评审报告.md`

**评审输出格式参见** [review-template.md](review-template.md)

## 问题发现与修改建议规范

### 问题发现要求

1. **穷举式检查**：必须逐条对照 review-checklist.md 中的每一项检查点进行审查，在报告的"检查清单覆盖情况"表中记录每项的审查结果
2. **不放过隐含问题**：除了显式错误外，重点关注以下隐含问题：
   - **逻辑漏洞**：条件分支不完整（缺少 else）、竞态条件、状态不一致
   - **隐式假设**：文档未说明但开发必须知道的前置条件或约束
   - **信息缺失**：某个操作提到了字段但未定义该字段的行为
   - **规则矛盾**：不同章节对同一事物的描述不一致
   - **歧义表达**：同一句话可以有多种理解方式
3. **跨模块审视**：利用阶段二的关系分析结果，检查模块间交互的潜在问题

### 修改建议规范

每个问题的修改建议必须满足以下标准：

1. **可直接采纳**：建议内容应具体到可以直接复制粘贴到需求文档中
2. **三种建议类型**：
   - **补充**：需求中遗漏的内容，提供应补充的完整文本
   - **修正**：需求中错误或不准确的内容，提供修改后的文本
   - **删除**：需求中矛盾或多余的内容，说明应删除的内容及原因
3. **定位精确**：指出应在需求文档的具体章节、段落或字段处进行修改
4. **示例驱动**：对于补充类建议，提供请求/响应示例或业务规则描述的示例文本

**修改建议示例**：

```markdown
##### 问题 3: 编辑接口缺少 purchasedQuantity 字段的类型和取值范围定义
- **严重等级**：🟡 一般
- **评审维度**：完整性
- **检查项编号**：1.2-③ 请求参数是否完整
- **问题描述**：purchasedQuantity 字段仅说明为"选填，代表买点"，未定义数据类型和取值范围
- **原文引用**：
  > 新增purchasedQuantity字段，选填，代表买点
- **影响分析**：开发人员可能对字段类型产生分歧（int 还是 decimal），导致实现不一致
- **修改建议**：
  - **建议类型**：补充
  - **修改位置**：第三章"编辑权益接口"的 purchasedQuantity 字段说明处
  - **建议内容**：
    新增purchasedQuantity字段（integer类型），选填，代表买点。
    取值范围：0 ≤ purchasedQuantity ≤ 999，仅支持整数。
    当传入该字段时，不可同时传入 quantity 字段。
```

## 执行要求

### 输出文件

评审过程会产生三个文件，保存在 `review-reports/` 目录：

```
review-reports/
├── {需求编号}-01-模块拆分.md
├── {需求编号}-02-关系分析.md
└── {需求编号}-03-评审报告.md
```

### 任务管理

使用 TodoWrite 工具跟踪评审进度：
- 将三个阶段分别作为独立任务
- 阶段三中每个模块的评审作为子任务
- 实时更新任务状态

### 交互规则

1. 开始前确认需求文档路径
2. 阶段一完成后，展示拆分概览并询问用户确认
3. 阶段二完成后，展示高风险关联点并询问用户确认
4. 阶段三逐模块评审，每个模块完成后简要汇报
5. 全部完成后输出评审总结

### 需求编号推断

- 如文档名包含 JIRA 编号（如 PAPI-2182），使用该编号
- 如文档名为中文名称，使用文档名简称
- 如无法推断，询问用户
