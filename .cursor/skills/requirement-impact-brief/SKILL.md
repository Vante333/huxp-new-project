# 需求派发 → 自动分析简报（强制）

用户原话：「需求派发给我之后会自动理解该需求并说明这个需求的测试范围，以及需求点，和影响范围」

当用户发来 **Jira 链接/单号、需求描述、截图说明、PRD 片段** 时，**不要只寒暄**，立即按本 skill 输出完整简报。

## 输入来源（尽量自动拉）

1. Jira：用 Atlassian 工具拉 summary/description/子任务/关联单  
2. 代码：在 `business-international-developer-api` 等仓库搜字段/枚举/Controller  
3. 已有用例/skill：`api-naming-catalog`、历史 testcases  
4. 信息不够：列出「待确认」最多 3 条，其余先按现有材料给可执行结论  

## 输出格式（固定五段，中文）

### 1. 一句话理解

用 1～2 句说明：改什么、为谁、结果长什么样。

### 2. 需求点

条目列表（不要编 R 编号对照表）。每条直接对应需求原文/字段/枚举/开关。  
未写清的标：`待确认：…`

### 3. 测试范围

写清 **测什么 / 不测什么**：

- **必测（P0）**：主路径、新字段/新枚举出现、对照配置源  
- **应测（P1）**：边界、多选组合、旧值回归、多品类抽样  
- **暂不测**：明确写「本需求未涉及：下单/支付/…」除非材料写了  

### 4. 影响范围

分维度：

| 维度 | 写什么 |
|------|--------|
| 系统 | Generic API / BOSS / SAAS / APP（有则写，无则写「无」） |
| 配置入口 | BOSS/SAAS 菜单或「仅接口入参」 |
| 数据/枚举 | 新增/变更的字段、枚举值 |
| 品类/模块 | Lounge、FT、Dining、会籍… |
| 兼容 | 旧枚举/旧链路是否要回归 |
| 文档/对外 | OpenAPI/Apifox 是否要更新 |

### 5. 影响接口（强制带命名）

每条必须：

```
METHOD /path — 中文名：干什么（本需求要验什么）
```

参考 `generate-test-cases/api-naming-catalog.md` 与本地 `d:\api\tools\api-lookup\`。  
同时给 **全链路顺序**（Token → … → 本需求卡点 → 回查）。

## 全链路卡环（帮助定范围）

```
① Token → ② 会籍/用户 → ③ 资源/可用性/权益 → ④ 下单 → ⑤ 支付/SSO/回调 → ⑥ 详情回查
```

先判断需求卡在第几环，再列 P0 接口（① + 本环 + 下一环）。

## 禁止

- 只丢 PATH 不写中文名和用途  
- 只说「回归一下」没有范围边界  
- 编造未在需求/代码中出现的接口行为  
- 把 BOSS/SAAS 对照写成含糊的「去后台看一下」（要写菜单路径或标明待确认）

## 与查接口网页的关系

- `d:\api\tools\api-lookup\index.html`：查 **API 全量路径 + 中文名**（人工检索）  
- **本 skill**：需求派发后的 **理解与范围简报**（在对话里自动做）  
- BOSS/SAAS 对照条目：用户明确要求再往网页里加，不默认塞全量后台接口  

## 示例口吻（结构示意）

用户发：`PAPI-3217 routeType 新增美国跨境区=7`

则输出应含：一句话理解 → 需求点（枚举 7）→ 测试范围（列表/详情/Hub；暂不测支付）→ 影响范围（BOSS 出发类型 → API routeTypes）→ 影响接口（带中文名的 3～N 个）+ 全链路顺序。
