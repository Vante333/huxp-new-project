# 技术方案评审技能

## 概述

从**测试工程师视角**对技术方案文档执行系统化评审，以需求文档为参照基准，检验技术方案是否完整、正确、可测试。

评审流程分为三个阶段：**方案解构 → 需求-方案映射分析 → 逐项评审**。

评审结果输出到 `review-reports/` 目录。

## 评审流程

### 阶段一：方案解构

**目标**：将技术方案文档解析为结构化的技术模块清单。

**操作步骤**：

1. 读取用户指定的技术方案文档
2. 读取关联的需求文档（如技术方案中引用的 JIRA 需求链接或用户指定的需求文档）
3. 按以下维度识别技术模块：
   - 文档标题层级（H2/H3 通常对应技术模块）
   - 涉及的接口/API 端点
   - 流程图/时序图覆盖的功能单元
   - 数据模型变更范围
4. 为每个模块提取：
   - **模块编号**：T1, T2, T3...
   - **模块名称**：简短描述
   - **涉及接口**：相关 API 端点列表
   - **技术要素**：包含的流程图、时序图、数据模型等
   - **关联需求**：对应的需求编号/功能点
   - **变更范围**：涉及修改的代码/服务/组件
5. 将解构结果保存到 `review-reports/{方案编号}-T01-方案解构.md`

**解构输出格式**：

```markdown
# {方案名称} - 方案解构

## 解构概览

| 模块编号 | 模块名称 | 涉及接口 | 关联需求 | 技术要素 |
|---------|---------|---------|---------|---------|
| T1 | xxx | /v2/xxx | PAPI-xxxx | 时序图、流程图 |
| T2 | xxx | /v2/xxx | PAPI-xxxx | 时序图 |

## T1: {模块名称}

### 涉及接口
- {接口路径及方法}

### 技术要素
- 时序图：{描述/引用}
- 流程图：{描述/引用}
- 数据模型：{描述/引用}

### 关联需求
- {需求编号}: {需求概述}

### 变更范围
- {修改的服务/组件/模块}

## T2: {模块名称}
...
```

### 阶段二：需求-方案映射分析

**目标**：分析需求文档和技术方案的映射关系，识别覆盖缺口和风险点。

**操作步骤**：

1. 基于阶段一的解构结果，逐一对照需求文档中的功能点
2. 建立双向映射：
   - **正向映射**：每个需求点是否有对应的技术方案
   - **反向映射**：每个技术模块是否有对应的需求来源
3. 识别以下问题：
   - **需求遗漏**：需求文档中有但技术方案未覆盖的功能点
   - **方案多余**：技术方案中有但需求文档未要求的内容（需确认是否为合理扩展）
   - **映射模糊**：无法明确判断对应关系的部分
4. 分析模块间依赖关系和执行顺序
5. 标记高风险点（强耦合、复杂交互、影响范围大）
6. 将分析结果保存到 `review-reports/{方案编号}-T02-映射分析.md`

**映射分析输出格式**：

```markdown
# {方案名称} - 需求-方案映射分析

## 覆盖度映射矩阵

| 需求点 | 需求描述 | 技术模块 | 覆盖状态 | 备注 |
|--------|---------|---------|---------|------|
| R1 | xxx | T1 | ✅ 已覆盖 | - |
| R2 | xxx | - | ❌ 未覆盖 | 技术方案中未提及 |
| R3 | xxx | T2 | ⚠️ 部分覆盖 | 缺少异常流程设计 |

## 模块依赖关系图（Mermaid）

（使用 mermaid graph 展示模块依赖）

## 覆盖缺口

### 缺口 1: {描述}
- **需求来源**：{需求编号/功能点}
- **缺失内容**：xxx
- **风险等级**：低/中/高
- **建议**：xxx

## 高风险点

### 风险点 1: {描述}
- **涉及模块**：T1, T3
- **风险说明**：xxx
- **测试关注点**：xxx
```

### 阶段三：逐项评审

**目标**：基于评审检查清单，从测试工程师视角系统化审查技术方案的质量，发现潜在问题和测试风险。

**核心原则**：

- **穷举式审查**：必须逐条对照 [tech-review-checklist.md](tech-review-checklist.md) 中的每一项检查点
- **测试视角**：始终从"这个方案我能不能测、好不好测、测试有什么风险"的角度出发
- **需求对照**：每个问题必须关联到需求文档中的对应描述或指出需求文档本身的缺失
- **原文引用**：问题描述中必须引用技术方案或需求文档的原始文本
- **建议可落地**：每个问题的修改建议必须具体到可直接用于修改技术方案

**操作步骤**：

1. 读取 [tech-review-checklist.md](tech-review-checklist.md) 获取完整检查清单
2. 按模块编号顺序逐个评审，每个模块按 8 个维度逐项检查：
   - **需求覆盖度**：技术方案是否完整覆盖需求文档中的所有功能点
   - **方案完整性**：流程图/时序图/数据模型是否完整
   - **方案正确性**：技术逻辑是否与需求一致，流程是否正确
   - **可测试性**：基于此方案能否编写测试用例，测试入口/出口是否清晰
   - **异常处理**：异常流程、错误处理、降级策略是否充分
   - **性能与并发**：是否考虑性能影响、并发安全
   - **兼容性与影响范围**：向后兼容、影响范围评估是否到位
   - **安全性**：是否有安全风险
3. 对每个问题评定严重等级：
   - 🔴 **严重**：方案有重大缺陷，可能导致功能实现错误或无法测试
   - 🟡 **一般**：方案需要补充或澄清，影响测试设计的准确性
   - 🟢 **建议**：优化建议，可提升方案质量和可测试性
4. 对每个问题给出修改建议
5. 给出每个模块的评审结论和整体评审总结
6. 将评审结果保存到 `review-reports/{方案编号}-T03-评审报告.md`

**评审输出格式参见** [tech-review-template.md](tech-review-template.md)

## 问题发现与修改建议规范

### 测试工程师关注重点

1. **需求到方案的可追溯性**：每个需求点是否都能在方案中找到对应的技术实现
2. **测试策略可制定性**：方案是否提供了足够信息来制定测试策略
3. **测试环境可构建性**：方案中的依赖和前置条件是否支持构建测试环境
4. **测试数据可准备性**：方案中的数据流转是否清晰到可以准备测试数据
5. **回归范围可确定性**：影响范围是否明确到可以确定回归测试范围

### 修改建议规范

每个问题的修改建议必须满足以下标准：

1. **可直接采纳**：建议内容应具体到可以直接用于修改技术方案
2. **三种建议类型**：
   - **补充**：方案中遗漏的内容，提供应补充的描述
   - **修正**：方案中错误或不准确的内容，提供修改后的描述
   - **细化**：方案中过于笼统的内容，提供应细化的方向和示例
3. **测试影响说明**：说明该问题对测试工作的具体影响

**修改建议示例**：

```markdown
##### 问题 2: 权益查询流程图缺少"无分级权益"的异常分支
- **严重等级**：🔴 严重
- **评审维度**：方案完整性
- **检查项编号**：2.1-③ 异常/错误分支是否在流程图中体现
- **问题描述**：流程图仅展示了"有等级权益"时置空字段的正常流程，缺少"查询不到等级权益"时的处理分支
- **原文引用**：
  > 查询所有权益模板下面是否设置了等级权益，有则置空 maxGuestsNextUse 和 allowedGuestsPerUsage 字段，没有则按旧逻辑计算
- **测试影响**：无法确定"无等级权益"场景的预期行为，测试用例无法设计该分支的验证点
- **修改建议**：
  - **建议类型**：补充
  - **修改位置**：2.1 权益查询逻辑 - 流程图
  - **建议内容**：
    在流程图中补充"否"分支的完整处理逻辑：
    1. 判断条件：查询权益模板未设置等级权益
    2. 处理方式：按旧逻辑计算 maxGuestsNextUse 和 allowedGuestsPerUsage
    3. 旧逻辑的计算规则引用或简要说明
```

## 执行要求

### 输出文件

评审过程会产生三个文件，保存在 `review-reports/` 目录：

```
review-reports/
├── {方案编号}-T01-方案解构.md
├── {方案编号}-T02-映射分析.md
└── {方案编号}-T03-评审报告.md
```

### 任务管理

使用 TodoWrite 工具跟踪评审进度：
- 将三个阶段分别作为独立任务
- 阶段三中每个模块的评审作为子任务
- 实时更新任务状态

### 交互规则

1. 开始前确认技术方案文档和需求文档的路径
2. 阶段一完成后，展示解构概览并询问用户确认
3. 阶段二完成后，展示覆盖缺口和高风险点并询问用户确认
4. 阶段三逐模块评审，每个模块完成后简要汇报
5. 全部完成后输出评审总结

### 方案编号推断

- 如技术方案关联 JIRA 编号（如 PAPI-2214），使用该编号
- 如技术方案有 Sprint 编号（如 Q1-SP4），使用该编号
- 如无法推断，询问用户
