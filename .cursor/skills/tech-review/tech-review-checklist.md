# 技术方案评审检查清单（测试工程师视角）

本清单用于阶段三逐项评审。评审时必须逐条检查，每个检查项标注 ✅（通过）或 ❌（未通过并记录问题）。

**编号规则**：`{大类编号}.{小类编号}-{序号}`，如 `1.2-③` 表示"需求覆盖度 → 接口覆盖 → 第3项"。

---

## 一、需求覆盖度检查

### 1.1 功能点覆盖
- [ ] ① 需求文档中的每个功能点是否都有对应的技术设计
  - 🔍 检查要点：逐一对照需求功能清单与技术模块
  - ⚠️ 常见问题：部分需求点在技术方案中被"隐式"实现但未说明
- [ ] ② 需求中的业务规则是否在技术方案中有体现
  - 🔍 检查要点：需求中的条件判断、计算规则是否在流程图/伪代码中反映
- [ ] ③ 需求中的异常场景是否在技术方案中有处理设计
  - 🔍 检查要点：需求中的错误码、异常分支是否在时序图/流程图中体现
- [ ] ④ 需求中新增/修改的字段是否在技术方案中有说明
  - 🔍 检查要点：字段的处理逻辑、存储方式、传递路径是否清晰

### 1.2 接口覆盖
- [ ] ① 需求涉及的每个接口是否都有技术方案
  - 🔍 检查要点：对比需求文档的接口列表与技术方案的接口列表
- [ ] ② 接口的请求/响应变更是否在技术方案中体现
  - 🔍 检查要点：新增字段、修改字段、废弃字段是否有说明
- [ ] ③ 接口间的调用关系是否在时序图中完整展示
  - 🔍 检查要点：上下游接口调用链路是否完整

### 1.3 非功能需求覆盖
- [ ] ① 性能要求是否在技术方案中有应对策略
- [ ] ② 并发要求是否在技术方案中有处理方案
- [ ] ③ 数据量级变化是否有评估

---

## 二、方案完整性检查

### 2.1 流程设计完整性
- [ ] ① 是否提供了清晰的业务流程图
  - 🔍 检查要点：流程图是否覆盖完整的业务路径
  - ⚠️ 常见问题：只画了主流程，缺少分支和异常路径
- [ ] ② 流程中的判断条件是否全部标注
  - 🔍 检查要点：每个菱形判断框是否有明确的"是/否"分支及条件
- [ ] ③ 异常/错误分支是否在流程图中体现
  - 🔍 检查要点：网络超时、数据异常、业务规则拒绝等异常路径
- [ ] ④ 流程的起点和终点是否明确
  - 🔍 检查要点：是否有明确的触发条件和结束状态

### 2.2 时序图完整性
- [ ] ① 是否提供了关键接口的时序图
  - 🔍 检查要点：核心接口是否有时序图展示调用链路
- [ ] ② 时序图中的参与者（服务/组件）是否完整
  - 🔍 检查要点：是否遗漏了关键的中间服务或外部依赖
- [ ] ③ 时序图中的消息/调用是否标注了关键参数
  - 🔍 检查要点：调用间传递的核心数据是否可见
  - ⚠️ 常见问题：只标注了方法名，缺少关键参数信息
- [ ] ④ 时序图中是否体现了异步调用和回调
  - 🔍 检查要点：如有异步操作，是否用虚线/特殊标记区分
- [ ] ⑤ 时序图是否覆盖异常场景的处理流程
  - 🔍 检查要点：调用失败时的处理路径是否展示

### 2.3 数据模型完整性
- [ ] ① 涉及数据变更时是否有数据模型/表结构说明
  - 🔍 检查要点：新增字段、新增表、修改字段是否有说明
- [ ] ② 数据流转路径是否清晰
  - 🔍 检查要点：数据从哪来、经过什么处理、存到哪里
- [ ] ③ 数据状态变更是否有状态机或状态流转说明
  - 🔍 检查要点：涉及状态变化的实体是否有状态流转图

### 2.4 变更范围完整性
- [ ] ① 是否明确列出了代码变更涉及的服务/模块
  - 🔍 检查要点：哪些服务需要修改代码
- [ ] ② 是否列出了影响到的现有功能
  - 🔍 检查要点：现有功能是否会受到本次变更影响
  - ⚠️ 常见问题：只说了"调个别场景回归即可"但未具体列出场景
- [ ] ③ 是否提供了回归测试建议
  - 🔍 检查要点：开发是否给出了需要回归的功能点清单

## 三、方案正确性检查

### 3.1 逻辑正确性
- [ ] ① 流程图/时序图中的逻辑是否与需求文档一致
  - 🔍 检查要点：技术实现逻辑是否准确还原了需求中的业务规则
  - ⚠️ 常见问题：技术方案中的判断条件与需求描述不一致
- [ ] ② 条件判断的分支处理是否正确
  - 🔍 检查要点：if/else 分支是否与需求中的业务规则对应
- [ ] ③ 数据处理逻辑是否正确
  - 🔍 检查要点：字段赋值、计算、转换逻辑是否与需求一致
- [ ] ④ 新旧逻辑的切换条件是否明确
  - 🔍 检查要点：涉及"旧逻辑"与"新逻辑"并存时，切换条件是否清晰

### 3.2 一致性
- [ ] ① 同一功能在不同图中的表述是否一致
  - 🔍 检查要点：流程图、时序图、文字描述三者是否对齐
- [ ] ② 接口路径与需求文档是否一致
  - 🔍 检查要点：技术方案中的接口路径是否与需求文档匹配
- [ ] ③ 字段命名在不同位置是否一致
  - 🔍 检查要点：同一字段在不同时序图/流程图中名称是否统一
- [ ] ④ 技术方案中引用的需求描述是否准确
  - 🔍 检查要点：方案中引用或概括的需求内容是否与原始需求一致

---

## 四、可测试性检查

### 4.1 测试入口与出口
- [ ] ① 每个技术模块是否有明确的测试入口（可触发的接口/操作）
  - 🔍 检查要点：测试人员能否通过接口或操作触发该功能
- [ ] ② 每个技术模块是否有可验证的输出（响应/状态/数据变化）
  - 🔍 检查要点：功能执行后能否通过接口或数据验证结果
- [ ] ③ 中间过程是否可观测（日志、监控、中间状态）
  - 🔍 检查要点：复杂流程的中间步骤是否有办法验证

### 4.2 测试数据
- [ ] ① 方案中的前置数据条件是否清晰
  - 🔍 检查要点：执行该功能前需要准备什么数据
  - ⚠️ 常见问题：方案假设某些数据已存在但未说明
- [ ] ② 数据之间的关联关系是否明确
  - 🔍 检查要点：数据间的外键关联、级联关系是否清晰
- [ ] ③ 特殊测试数据是否可构造
  - 🔍 检查要点：边界值数据、异常状态数据是否能通过接口构造

### 4.3 测试策略可制定性
- [ ] ① 方案是否提供了足够信息来确定测试范围
  - 🔍 检查要点：新增功能、修改功能、影响范围是否清晰
- [ ] ② 方案是否提供了足够信息来确定测试优先级
  - 🔍 检查要点：核心变更 vs 影响范围 vs 风险程度是否可判断
- [ ] ③ 方案是否提供了足够信息来设计测试场景
  - 🔍 检查要点：正常流、异常流、边界条件是否都能据方案设计用例

---

## 五、异常处理检查

### 5.1 错误处理
- [ ] ① 外部服务调用失败时的处理方案是否明确
  - 🔍 检查要点：调用下游服务超时/异常时如何处理
  - ⚠️ 常见问题：时序图中只画了正常调用链路
- [ ] ② 数据查询为空时的处理方案是否明确
  - 🔍 检查要点：查不到数据时是报错还是返回默认值
- [ ] ③ 参数校验失败时的处理方案是否明确
  - 🔍 检查要点：非法参数的拦截和错误返回
- [ ] ④ 业务规则校验失败时的处理方案是否明确
  - 🔍 检查要点：不满足业务条件时的处理方式和错误码

### 5.2 降级与兜底
- [ ] ① 关键依赖不可用时是否有降级方案
  - 🔍 检查要点：核心功能的降级策略
- [ ] ② 是否有兜底逻辑避免系统崩溃
  - 🔍 检查要点：极端情况下的保护机制
- [ ] ③ 降级后的用户体验是否有说明
  - 🔍 检查要点：降级时用户看到什么、功能受什么影响

### 5.3 幂等与重试
- [ ] ① 接口是否需要幂等设计，方案中是否有体现
- [ ] ② 重试机制是否明确（重试次数、间隔、条件）
- [ ] ③ 重复请求的处理策略是否说明

---

## 六、性能与并发检查

### 6.1 性能影响
- [ ] ① 新增逻辑是否引入额外的数据库查询或服务调用
  - 🔍 检查要点：新增的查询/调用对响应时间的影响
- [ ] ② 循环/批量操作是否有性能风险
  - 🔍 检查要点：是否存在 N+1 查询、大批量数据处理
- [ ] ③ 是否有缓存策略的变更或引入
  - 🔍 检查要点：缓存的粒度、过期策略、一致性

### 6.2 并发安全
- [ ] ① 共享数据的并发修改是否有保护机制
  - 🔍 检查要点：是否需要加锁、乐观锁、事务隔离
- [ ] ② 并发场景下的数据一致性是否有保证
  - 🔍 检查要点：多个请求同时操作时是否可能产生脏数据

---

## 七、兼容性与影响范围检查

### 7.1 向后兼容
- [ ] ① 接口变更是否向后兼容
  - 🔍 检查要点：新增字段是否为选填、响应结构变更是否兼容旧版本
- [ ] ② 新逻辑是否影响现有功能的正常使用
  - 🔍 检查要点：在不使用新功能的情况下，现有功能是否正常
- [ ] ③ 数据库变更是否向后兼容
  - 🔍 检查要点：新增字段是否有默认值、旧数据是否需要迁移

### 7.2 影响范围评估
- [ ] ① 影响范围描述是否具体、可操作
  - 🔍 检查要点：是否具体到接口/页面/功能点级别
  - ⚠️ 常见问题："影响范围不大"、"调个别场景回归即可"等模糊描述
- [ ] ② 影响的上下游系统/服务是否列出
  - 🔍 检查要点：是否有外部系统受影响
- [ ] ③ 是否给出了回归测试的具体建议
  - 🔍 检查要点：建议回归哪些功能、哪些接口

---

## 八、安全性检查

### 8.1 数据安全
- [ ] ① 敏感数据处理是否有安全措施
  - 🔍 检查要点：涉及用户信息、权益数据时的处理方式
- [ ] ② 数据权限控制是否在技术方案中体现
  - 🔍 检查要点：不同角色/租户的数据隔离

### 8.2 接口安全
- [ ] ① 接口鉴权是否在技术方案中体现
  - 🔍 检查要点：新接口或修改接口的鉴权方式
- [ ] ② 参数校验策略是否在方案中体现
  - 🔍 检查要点：防注入、防越权等安全措施

---

## 九、文档质量检查

### 9.1 图表质量
- [ ] ① 流程图/时序图是否清晰可读
  - 🔍 检查要点：图片分辨率、标注文字是否可辨识
  - ⚠️ 常见问题：图片过小、文字模糊
- [ ] ② 图表与文字描述是否对应
  - 🔍 检查要点：图中展示的逻辑与文字说明是否一致
- [ ] ③ 图表中的术语/命名是否与需求文档一致
  - 🔍 检查要点：方法名、字段名、服务名是否统一

### 9.2 描述质量
- [ ] ① 技术方案描述是否有歧义
  - 🔍 检查要点：是否存在多义理解的表述
  - ⚠️ 常见问题："按旧逻辑计算"但未说明旧逻辑是什么
- [ ] ② 技术术语是否准确使用
  - 🔍 检查要点：方法名、接口名、字段名是否与代码一致
- [ ] ③ 章节编号/命名是否有冲突
  - 🔍 检查要点：是否存在重复的章节名称（如两个"权益明细接口"）
